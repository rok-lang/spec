# 1.1. 포인터 계열: `Ptr` / `ConstPtr` / `ManyPtr` / `CPtr`

`rok::bare::ptr` 모듈은 원시 포인터 다섯 종을 정의합니다. 설계는 Zig 식 arity-encoded 모델을 따릅니다. 가리키는 개수(arity)와 가변성을 타입 자체에 인코딩해서, 소리 없는 강제 변환(silent coercion)을 원천 차단합니다.

## 1.1.1. 포인터 5종

다섯 종류는 다음과 같이 나뉩니다.

| 타입          | 의미                            | C 대응          | nullable                 |
|---------------|---------------------------------|-----------------|--------------------------|
| `Ptr<T>`      | 가변, 정확히 1개 T             | `T*`            | ✗ (`Ptr<T> \| none` 사용) |
| `ConstPtr<T>` | const, 정확히 1개 T            | `const T*`      | ✗                        |
| `ManyPtr<T>`  | 가변, 연속 N개 T (길이 모름)    | `T*` (배열)     | ✗                        |
| `Slice<T>`    | 가변, 연속 N개 T (길이 포함)    | (T*, len)       | ✗ (별도 niche)           |
| `CPtr<T>`     | C 호환 **nullable** + 1개      | `T*` (nullable) | ✓ (자동)                 |

`Ptr`, `ConstPtr`, `ManyPtr`, `CPtr`는 `#[repr(transparent)]`이므로 `extern "C"` 경계에서는 C 포인터입니다.

이 가운데 `Slice<T>`는 [2.9 collections](../200-core/209-collections.md)에서 정의하는 안전한 뷰입니다. 이 모듈은 포인터에서 `Slice`로 가는 경로(`ManyPtr::slice`)만 정의합니다. 리스트 원소를 가리키는 포인터는 pin에서 얻습니다([1.6](106-gc-pin.md)).

### `Send` / `Sync`

원시 포인터 `Ptr<T>`, `ConstPtr<T>`, `ManyPtr<T>`, `CPtr<T>`는 모두 `!Send`, `!Sync`입니다([2.13.9](../200-core/213-marker.md#2139-send--sync-스레드-경계-마커)). 포인터를 담은 타입을 스레드 사이로 넘기려면 작성자가 `unsafe impl Send`로 보증해야 합니다.

### 자동 niche

`Ptr<T>`, `ConstPtr<T>`, `ManyPtr<T>`는 null 포인터 값을 niche로 쓸 수 있습니다. 그래서 `none`을 추가해도 별도 태그가 필요 없습니다. 다만 이 동작은 최적화일 뿐 보장이 아닙니다. 구현은 `Ptr<T> | none`을 일반 태그 합 타입으로 표현해도 됩니다.

```rok
size_of::<Ptr<i32>>()         //→ 8 (64-bit target)
size_of::<Ptr<i32> | none>()  //→ 8 (niche 를 쓰는 구현, 보장 아님)
```

반면 `CPtr<T>`는 그 자체로 nullable이라 별도 센티넬이 필요 없습니다. `none` 표현은 그냥 `CPtr::null()`입니다.

niche 메커니즘은 [2.2 non-zero](../200-core/202-non-zero.md)에 있습니다.

## 1.1.2. `Ptr<T>`: strict provenance API

가장 기본 타입인 `Ptr<T>`의 공개 API입니다.

```rok
struct Ptr<T> { /* opaque (address, provenance) pair */ }

impl<T> Ptr<T> {
    // 생성
    fn dangling() -> Ptr<T>;           // valid alignment, invalid address (unique)
    fn null() -> Ptr<T> | none;         // 항상 none

    // provenance-preserving (strict provenance, 안전 우선)
    fn addr(self) -> usize;             // 주소만 (provenance 손실)
    fn with_addr(self, addr: usize) -> Ptr<T>;
                                        // provenance 보존, address 변경
    fn map_addr(self, f: fn(usize) -> usize) -> Ptr<T>;

    // 산술 (provenance 보존)
    fn offset(self, count: isize) -> Ptr<T>;       // count * sizeof(T) byte offset
    fn add(self, count: usize) -> Ptr<T>;
    fn sub(self, count: usize) -> Ptr<T>;
    fn byte_offset(self, count: isize) -> Ptr<T>;  // byte 단위 offset

    fn distance(self, origin: Ptr<T>) -> isize;     // self.addr() - origin.addr()
    fn is_aligned(self) -> bool;
    fn align_offset(self, align: usize) -> usize;

    // 같은 주소, 다른 view (alignment 는 호출자 책임)
    fn cast<U>(self) -> Ptr<U>;
    fn as_const(self) -> ConstPtr<T>;
    fn as_many(self) -> ManyPtr<T>;

    // dereference (UB if invalid)
    unsafe fn read(self) -> T;
    unsafe fn write(self, value: T);
    unsafe fn read_volatile(self) -> T;
    unsafe fn write_volatile(self, value: T);
}
```

```rok
// module functions of rok::bare::ptr
fn size_of<T>() -> usize;              // rok::bare::mem::size_of 로도 노출
fn align_of<T>() -> usize;
fn addr_of<T>(place: T) -> Ptr<T>;
fn many_addr_of<T>(place: T) -> ManyPtr<T>;
fn expose_provenance<T>(p: Ptr<T>) -> usize;
unsafe fn from_exposed_provenance<T>(addr: usize) -> Ptr<T>;
```

`addr_of` / `many_addr_of`는 place 식을 받습니다. 지역 변수나 `static`(`extern "C"` `static` 포함), 또는 그 필드나 원소입니다. 지역 변수를 가리키는 포인터는 그 변수가 스코프에 있는 동안 유효합니다. static을 가리키는 포인터는 실행 내내 유효합니다. static은 데이터 섹션에 있습니다. 지연 초기화 static은 주소를 취하기 전에 초기화됩니다. static이 쥔 GC 참조는 루트입니다. `mut`가 아닌 static을 가리키는 포인터로 쓰면 미정의 동작입니다. 주소를 취한 변수는 그 스코프 동안 GC 루트로 남습니다. 루트는 고정되므로 가리키는 대상은 움직이지 않습니다. 코루틴 본체에서는 포인터가 다음 중단 지점까지만 유효합니다. 그런 포인터를 중단 지점 뒤에 쓰면 컴파일 에러입니다.

### Strict provenance: escape hatch 분리

컴파일러는 `usize → Ptr<T>` 변환을 기본으로 거부합니다. provenance를 잃은 포인터를 역참조하면 UB이기 때문입니다. 그래서 정상 경로와 탈출구(escape hatch)를 명확히 나눕니다.

```rok
// 권장: provenance 보존
let p: Ptr<i32> = ...;
let q = p.with_addr(p.addr() + 4);     // 4 byte 다음, provenance 그대로

// 비권장: provenance 새로 (FFI / hardware register 자리에서만)
use rok::bare::ptr::{expose_provenance, from_exposed_provenance};

let exposed: usize = expose_provenance(p);   // p 의 provenance 를 "노출"
let r: Ptr<i32> = unsafe { from_exposed_provenance(exposed) };
                                              // 새로 만든 ptr 이 노출된 provenance 중
                                              // 하나를 가진다고 _가정_
```

이 설계의 출발점은 [Ralf Jung의 "Pointers Are Complicated"](https://www.ralfj.de/blog/2022/04/11/provenance-exposed.html) 글입니다. 2024년 12월 Rust 1.84에서 안정화된 `core::ptr::with_exposed_provenance`와 같은 모델입니다.

### 예: 포인터 산술

산술은 다음과 같이 씁니다.

```rok
let arr: [i32; 5] = [10, 20, 30, 40, 50];
let p: Ptr<i32> = rok::bare::ptr::addr_of(arr[0]);

let p3 = p.add(3);                    // arr[3] 의 ptr
unsafe {
    let v = p3.read();                //→ 40
}

// byte 산술 (struct field offset)
struct Header { magic: u32; size: u64; }
let h: Ptr<Header> = ...;
let size_ptr: Ptr<u64> = h.byte_offset(4).cast::<u64>();
                                      // Header.size 의 위치
                                      // (정렬 검증 필요, 1.2 cast 참조)
```

## 1.1.3. `ConstPtr<T>`: read-only

읽기 전용 변종에는 쓰기 계열 메서드가 없습니다.

```rok
struct ConstPtr<T> { /* opaque */ }

impl<T> ConstPtr<T> {
    fn dangling() -> ConstPtr<T>;

    fn addr(self) -> usize;
    fn with_addr(self, addr: usize) -> ConstPtr<T>;
    fn offset(self, count: isize) -> ConstPtr<T>;
    fn add(self, count: usize) -> ConstPtr<T>;
    fn sub(self, count: usize) -> ConstPtr<T>;

    fn cast<U>(self) -> ConstPtr<U>;
    fn as_many(self) -> ManyPtr<T>;

    unsafe fn read(self) -> T;
    unsafe fn read_volatile(self) -> T;
    // write 메서드 없음: read-only
}
```

`Ptr<T>`와 주고받는 변환은 방향에 따라 안전성이 다릅니다. const를 붙이는 쪽은 자유롭습니다. 떼는 쪽은 이름 있는 캐스트 `rok::bare::const_cast`를 거쳐야 합니다. 호출 자체는 안전하고, 결과로 쓰기를 하는 동작이 `unsafe`입니다.

```rok
let m: Ptr<i32> = ...;
let c: ConstPtr<i32> = m.as_const();        // Ptr → ConstPtr (안전)

let c: ConstPtr<i32> = ...;
let m: Ptr<i32> = rok::bare::const_cast(c);    // ConstPtr → Ptr (호출은 안전, m 을 통한 쓰기는 unsafe, 1.2 cast 참조)
```

따라서 const 제거는 **명시적** 경로로만 일어납니다. 소리 없는 변환은 허용하지 않습니다.

## 1.1.4. `ManyPtr<T>`: 연속 N개, 길이 모름

길이 정보 없이 여러 원소를 가리키는 타입입니다.

```rok
struct ManyPtr<T> { /* opaque */ }

impl<T> ManyPtr<T> {
    fn addr(self) -> usize;
    fn with_addr(self, addr: usize) -> ManyPtr<T>;

    fn offset(self, count: isize) -> ManyPtr<T>;
    fn add(self, count: usize) -> ManyPtr<T>;

    fn as_one(self) -> Ptr<T>;                  // 첫 원소
    fn as_const(self) -> ConstPtr<T>;

    unsafe fn read(self, idx: usize) -> T;
    unsafe fn write(self, idx: usize, value: T);

    // 길이 정보 없음. index 호출자가 보장
    unsafe fn slice(self, len: usize) -> Slice<T>;        // length 부착하여 Slice 만듬
}
```

C의 `T*`(배열)를 받을 때 씁니다. 길이 정보가 없으므로 범위 밖 접근(OOB)을 피할 책임은 호출자에게 있습니다. GC 힙 밖의 메모리를 보는 `slice`에는 GC 참조가 든 원소를 담으면 안 됩니다. 담으면 미정의 동작입니다.

```rok
extern "C" {
    fn read_buffer(out: ManyPtr<u8>, len: usize) -> usize;
}

let buf: [u8; 1024] = [0; 1024];
let read_count = unsafe {
    read_buffer(rok::bare::ptr::many_addr_of(buf[0]), 1024)
};
```

## 1.1.5. `CPtr<T>`: C 호환, null 가능

C ABI와 바로 이어지는 nullable 변종입니다.

```rok
struct CPtr<T> { /* opaque, nullable */ }

impl<T> CPtr<T> {
    fn null() -> CPtr<T>;
    fn from_ptr(p: Ptr<T>) -> CPtr<T>;       // non-null
    fn from_const(p: ConstPtr<T>) -> CPtr<T>;
    fn from_addr(addr: usize) -> CPtr<T>;    // 0 = null

    fn is_null(self) -> bool;
    fn as_ptr(self) -> Ptr<T> | none;        // null → none
    fn as_const(self) -> ConstPtr<T> | none;

    fn addr(self) -> usize;                  // null = 0
}
```

C 함수가 nullable `T*`를 주고받는 경계에서 씁니다. 전형적인 쓰임은 다음과 같습니다.

```rok
extern "C" {
    fn malloc(size: usize) -> CPtr<u8>;       // 실패 시 null
    fn free(ptr: CPtr<u8>);
}

let buf: CPtr<u8> = unsafe { malloc(1024) };
match buf.as_ptr() {
    p: Ptr<u8> => use(p),
    none       => panic("malloc failed"),
}
unsafe { free(buf) };
```

`Ptr<T> | none`은 자동 niche 덕분에 ABI가 호환됩니다. 하지만 `-1`처럼 **명시 센티넬**이 필요한 곳에서는 `CPtr`만으로 부족합니다. 이때는 newtype에 `#[niche(-1)]`을 붙여 따로 모델링하는 방법이 정석입니다.

## 1.1.6. 변환 매트릭스

다섯 타입 사이의 변환 경로를 한 표로 정리합니다.

| from \ to     | `Ptr<T>` | `ConstPtr<T>` | `ManyPtr<T>` | `CPtr<T>` | `Slice<T>` | `usize` |
|---------------|----------|---------------|--------------|-----------|------------|---------|
| `Ptr<T>`      | - | `.as_const()` 안전 | `.as_many()` 안전 | `CPtr::from_ptr(p)` | `.as_many().slice(len)` unsafe | `.addr()` provenance 손실 |
| `ConstPtr<T>` | `rok::bare::const_cast(c)` | - | `.as_many()` | `CPtr::from_const(c)` | `.as_many().slice(len)` unsafe | `.addr()` |
| `ManyPtr<T>`  | `.as_one()` 안전 | `.as_const()` | - | `CPtr::from_ptr(m.as_one())` | `.slice(len)` unsafe | `.addr()` |
| `CPtr<T>`     | `.as_ptr()?` | `.as_const()?` | `.as_ptr()?.as_many()` | - | `.as_ptr()?.as_many().slice(len)` unsafe | `.addr()` |
| `Slice<T>`    | `pin.as_data_ptr()` | `pin.as_data_ptr().as_const()` | `pin.as_data_many_ptr()` | `CPtr::from_ptr(pin.as_data_ptr())` | - | `pin.as_data_ptr().addr()` |
| `usize`       | `from_exposed_provenance(a)` ⚠ | `from_exposed_provenance(a).as_const()` ⚠ | `from_exposed_provenance(a).as_many()` ⚠ | `CPtr::from_addr(a)` | 포인터 경유 | - |

⚠ 표시는 provenance를 새로 만드는 탈출구라는 뜻입니다. `Slice<T>`에는 자체 포인터 접근자가 없습니다. 그 행의 `pin`은 슬라이스가 보는 `List<T>`를 고정하는 `gc::pin(xs)`입니다. 포인터는 리스트의 첫 원소를 가리키고, 그 pin이 유지되는 동안만 유효합니다([1.6](106-gc-pin.md)).

## 1.1.7. 다른 언어와 비교

같은 문제를 다뤄 온 다른 언어와 비교하면 다음과 같습니다.

| 측면              | C           | Rust                  | Zig                    | Rok                            |
|-------------------|-------------|-----------------------|------------------------|--------------------------------|
| 1개 포인터        | `T*`        | `*const T` / `*mut T` | `*T` / `*const T`      | `Ptr<T>` / `ConstPtr<T>`       |
| 다수 포인터       | `T*` (모호) | `*const T` (모호)     | `[*]T`                 | `ManyPtr<T>`                   |
| length-aware      | **없음**    | `&[T]`                | `[]T`                  | `Slice<T>`                     |
| nullable          | (모든 포인터) | `Option<*const T>`    | `?*T`                  | `CPtr<T>` 또는 `Ptr<T> \| none` |
| arity 분리        | **없음**    | **부분** (slice 별도) | ✓ (`*T` / `[*]T` 분리) | ✓ (Zig 모델)                   |
| strict provenance | **없음**    | ✓ (1.84+)             | **없음**               | ✓ (Rust 모델)                  |
| `as` cast 거부    | **허용**    | **허용** (경고만)    | **명시 `@ptrCast`**    | **완전 거부**                  |

Rok의 가장 중요한 결정은 세 가지입니다. 첫째, Zig 식 arity 분리를 받아들여 다섯 종류를 명확히 나눴습니다. 둘째, strict provenance는 Rust 2024 모델을 채택했습니다. 셋째, 명시 캐스트를 강제해서 포인터에는 `as`를 아예 쓸 수 없습니다. 이 세 결정으로 C와 Rust의 포인터 함정 대부분을 피합니다.
