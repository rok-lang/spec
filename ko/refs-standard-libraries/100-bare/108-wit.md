# 1.8. WASM Component Model - `ffi.wit`

WebAssembly Component Model ([bytecodealliance.org](https://component-model.bytecodealliance.org/), Preview 2는 2024년 1월에 안정화되었습니다)은 타입이 있는 언어 간 인터페이스를 정의하는 기반입니다. 전통적인 C ABI FFI([1.7](107-ffi.md))가 쓰던 raw pointer와 길이 쌍 모델을 record / variant / resource 같은 풍부한 타입으로 대체합니다.

## 1.8.1. WIT - WebAssembly Interface Types

WIT는 언어 중립적인 인터페이스 정의 언어입니다.

```wit
package example:fs;

interface fs {
    record stat {
        size: u64,
        mtime: u64,
        is-dir: bool,
    }

    variant error {
        not-found,
        permission-denied,
        io-error(string),
    }

    resource file {
        constructor(path: string);
        read: func(buf-size: u32) -> result<list<u8>, error>;
        close: func();
    }

    open: func(path: string) -> result<file, error>;
}
```

이렇게 정의한 인터페이스는 Rust, Go, Python, Rok 등 어떤 언어에서든 import하거나 export할 수 있습니다.

## 1.8.2. Rok 측 binding 형태

import 측은 외부 component를 씁니다. 여기서 `wit/fs.wit`는 맨 위에 `package example:fs;`를 둔 1.8.1의 interface입니다.

```rok
ffi::wit::import { "wit/fs.wit" }       // 이 소스 파일 기준 상대 경로

use example::fs::fs::{File, Error};

let f = File::new("data.txt");
let bytes = try f.read(1024);           // throws (Error) -> List<u8>
f.close();
```

export 측은 component를 제공합니다. `calculator.wit`는 world 안에 `add: func(a: s32, b: s32) -> s32`를 선언합니다.

```rok
ffi::wit::export { "calculator.wit" }

#[wit::export]
fn add(a: i32, b: i32) -> i32 { a + b }
```

### 경로와 위치

- 경로는 소스 파일 기준 상대 경로입니다. `.wit` 파일이나 package 디렉토리를 가리키며, package 디렉토리의 의존 패키지는 그 `deps/`에 있습니다.
- 이 항목은 프로그램의 패키지와 의존 패키지에서 쓸 수 있습니다. binding은 그 항목이 있는 모듈(의존 패키지라면 그 의존 패키지의 모듈) 안의 `ns::pkg::iface`(`wasi::filesystem::types`) 아래에 들어갑니다.
- WIT 타입은 PascalCase Rok 타입이 됩니다(`descriptor-type` → `DescriptorType`, `file` → `File`). 함수와 필드는 snake_case가 됩니다.

### World

이름 붙은 파일의 world는 그 component 자체입니다. 그렇지 않으면 키워드가 정합니다. `ffi::wit::import`는 interface를 import하고, `ffi::wit::export`는 export합니다. `include ... with { a as b }`는 포함한 항목의 이름을 바꿉니다.

### 타입 대응

| WIT                    | Rok                                                         |
|------------------------|-------------------------------------------------------------|
| `record`               | `struct`                                                    |
| `variant`, `enum`      | `enum`                                                      |
| `flags`                | `Default`를 가진 `bool` 필드의 `struct` (flag 32개까지)   |
| `option<T>`            | `T?` (중첩 option은 층을 유지: `option<option<T>>` → `T??`) |
| `result<T, E>`         | `Result<T, E>`. 이것을 돌려주는 함수는 `throws (E) -> T`    |
| `tuple<..>`            | 튜플                                                        |
| `list<T>`              | `List<T>`                                                   |
| `list<T, N>`           | `[T; N]`                                                    |
| `string`               | `str` (UTF-8)                                               |
| `char`, `bool`, `f32`, `f64` | 같음                                                  |
| `sN` / `uN`            | `iN` / `uN`                                                 |
| `future<T>`            | `AsyncFuture<T>`                                            |
| `stream<T>`            | `rok::core::channel::Receiver<T>` (sender를 닫으면 끝남)   |
| `error-context`        | `rok::bare::ffi::wit::ErrorContext`                         |
| import한 `resource`   | `using` / `Drop`으로 해제되는 handle struct                |
| export하는 `resource` | 사용자의 `#[wit::export] pub struct`                        |

### Async

`async func`는 import와 export 모두에서 `async fn`입니다. 동기 task(preview 2의 `main`, 동기 export)는 component model을 기다릴 수 없고 기다리면 런타임 panic이므로, async import는 async export 안에서 await합니다. preview 3 command는 `wasi:cli/run@0.3.x`를 `#[wit::export] async fn run() -> Result<(), ()>`로 export합니다. async export 호출은 동시에 실행되며, 각 호출이 component model task 하나입니다. 호출은 자기 차례에 결과를 돌려줍니다. async export 안에서 socket과 timer는 host의 event 사이에서 기다리며, component model event도 대기 중이면 적어도 10 ms마다 확인합니다(preview 2 pollable과 component model의 event를 한꺼번에 기다릴 수 없기 때문입니다). 아무도 전해 주지 않는 것을 기다리는 async export는 계속 기다립니다. 다른 호출이 그것을 전해 줄 수도 있습니다.

생성된 binding이 호출하는 async canonical ABI는 `rok::std::wit`에 있습니다. executor 위에서 돌며, `stream<T>`는 core 타입에 대응합니다. 메모리 helper, block, handle, `ErrorContext`는 `rok::bare::ffi::wit`에 남습니다.

### Export

export 함수는 그 항목의 모듈에 있는 `#[wit::export] fn`이며, snake_case 이름으로 WIT 함수와 짝지어집니다. export하는 resource는 `#[wit::export] pub struct`이고, 그 `impl`이 `new`(constructor), 메서드, static 함수를 정의합니다. 실패할 수 있는 constructor(`result<r, ..>`)는 throw하는 `new`이며, resource의 destructor는 그 `Drop`을 실행합니다. 빠진 export는 컴파일 에러입니다.

WIT를 export하고 진입 파일에 `fn main`도 top-level 문도 없는 패키지는 reactor입니다. reactor는 `wasi:cli/run`을 export하지 않습니다([4.16.1](../../refs-lang/004-functions/416-entry-point.md#4161-진입-모듈-mainrok)).

### 타깃

WIT에는 `wasm32-wasi`(WASI preview 2 component)가 필요하며, 다른 타깃에서는 컴파일 에러입니다. export는 `main`보다 먼저 호출될 수 있습니다. 런타임은 첫 export 호출에서 시작합니다.

미리 빌드한 의존 패키지는 그 `ffi::wit` 항목이 읽는 `.wit` 파일을 ROKHIR에 담고 다닙니다([refs-lang 9.4.7](../../refs-lang/009-tools/904-rokhir-bytecode.md#947-body)). 의존하는 쪽은 그 파일을 디스크에서 읽지 않습니다.

### 제약

import한 interface는 component가 export하는 interface의 타입을 쓸 수 없으며, 쓰면 컴파일 에러입니다.

### binding runtime - `rok::bare::ffi::wit`

생성된 binding이 이 helper를 호출하며, 일반 코드는 binding을 씁니다. block은 C allocator에서 오며, host가 `cabi_realloc`으로 채우는 block도 마찬가지입니다. lift된 string이나 list는 GC 메모리로 복사된 뒤 자기 block을 해제합니다. import 호출 하나가 block에 lower한 값은 호출 뒤 함께 해제되고, export의 값은 그 export의 post-return 함수가 해제합니다.

```rok
// rok::bare::ffi::wit: canonical ABI 주소 (i32) 의 linear memory
unsafe fn load_u8(a: i32) -> u8;      // load_u16 / load_i32 / load_i64 / load_f32 / load_f64 도 같음
unsafe fn store_u8(a: i32, v: u8);    // store_u16 / store_i32 / store_i64 / store_f32 / store_f64 도 같음

// variant 의 합쳐진 flat slot
fn f32_bits(x: f32) -> i32;
fn f32_from(x: i32) -> f32;
fn f64_bits(x: f64) -> i64;
fn f64_from(x: i64) -> f64;
fn char_from(x: i32) -> char;         // scalar 가 아니면 panic
fn bad_case() -> !;                   // panic: 범위 밖 discriminant

const BLOCKED: i32 = -1;              // copy 나 호출이 곧바로 끝나지 않음
const DROPPED: i32 = 1;               // copy 의 상대편이 drop 됨

unsafe fn free(a: i32);
unsafe fn str_take(p: i32, n: i32) -> str;          // 복사한 뒤 block 을 해제
unsafe fn bytes_take(p: i32, n: i32) -> List<u8>;   // 복사한 뒤 block 을 해제

struct Blocks { /* private */ }
impl Blocks {
    fn new() -> Blocks;
    fn alloc(self, size: i32, align: i32) -> i32;   // 빈 block 은 주소 `align`
    fn str(self, s: str) -> (i32, i32);             // (주소, 길이)
    fn bytes(self, l: List<u8>) -> (i32, i32);      // (주소, 길이)
    fn free(self);                                  // 모든 block 을 해제
}

struct Handle { /* private */ }
impl Handle {
    fn own(h: i32) -> Handle;
    fn borrowed(h: i32) -> Handle;
    fn get(self) -> i32;                  // drop 되거나 넘겨진 뒤에는 panic
    fn take(self) -> i32;                 // own 을 넘김; borrow 면 panic
    fn release(self) -> i32 | none;       // 아직 소유 중이면 drop 할 handle
}

struct Table<T> { /* private */ }
unsafe impl<T> Sync for Table<T> {}
impl<T> Table<T> {
    unsafe fn new() -> Table<T>;          // 한 번에 한 스레드만 쓰도록 호출자가 보장
    fn insert(self, v: T) -> i32;         // rep
    fn get(self, rep: i32) -> T;          // take 된 뒤에는 panic
    fn take(self, rep: i32) -> T?;        // slot 을 해제; 이미 take 됐으면 none
}

struct ErrorContext { /* private */ }
impl ErrorContext {                       // wasm32-wasi 전용
    fn new(msg: str) -> ErrorContext;
    fn debug_message(self) -> str;        // host 가 빈 메시지를 줄 수 있음
    fn raw(self) -> i32;
    fn from_raw(h: i32) -> ErrorContext;
}
impl Drop for ErrorContext { /* error-context.drop */ }
```

`Handle`의 복사본은 cell 하나를 공유합니다. `own`을 넘기거나 drop하면 모든 복사본이 비워집니다. `Table<T>`는 export한 resource의 값을 표현(`rep`)별로 보관하며, host가 그 handle을 drop할 때(`[dtor]`)까지 유지합니다.

## 1.8.3. C FFI vs WIT 차이

두 방식은 여러 면에서 다릅니다.

| 측면        | C FFI ([1.7](107-ffi.md))    | WIT (이 장)                 |
|-------------|------------------------------|-----------------------------|
| 타입 시스템 | C primitive + 사용자 struct  | record / variant / resource |
| 안전성      | **낮음** (raw ptr 손수 관리) | **높음** (typed)            |
| 메모리 관리 | malloc/free                  | resource (자동 destructor)  |
| 에러 처리   | errno / 반환값 convention    | result<T, E> 1급            |
| String      | null-terminated              | length-prefixed UTF-8       |
| List        | (ptr, len) manual            | list<T> 자동                |
| 호출 비용   | 거의 없음 (direct call)      | trampoline (~ns)            |
| 적용 범위   | 모든 native target           | `wasm32-wasi` (preview 2 component) |
| unsafe 필요 | ✓                            | ✗                           |

## 1.8.4. 선택 기준

기준은 단순합니다. 무엇을 호출하고 어디에 배포하는지에 따라 정합니다.

| 시나리오                    | 권장                      |
|-----------------------------|---------------------------|
| 전통 C 라이브러리 호출      | C FFI ([1.7](107-ffi.md)) |
| 시스템 콜 (libc, Win32)     | C FFI                     |
| GPU / SIMD intrinsic        | C FFI                     |
| 다른 언어와 안전 인터페이스 | WIT                       |
| WASM 환경 배포              | WIT                       |
| 플러그인 / 샌드박스 격리    | WIT                       |
| Modular / Mojo 등 다국어    | WIT                       |

Rok은 전통 C FFI와 WIT를 모두 지원합니다. 사용자는 안전성, 성능, target 환경의 제약에 맞춰 한쪽을 고르면 됩니다.
