# 2.5. 비교 트레잇

이 장은 값 사이의 비교를 정의하는 트레잇 패밀리를 다룹니다. `==`, `!=`, `<`, `>`, `<=`, `>=` 연산자뿐 아니라 해시, 정렬, 패턴 매칭도 이 장의 트레잇으로 디스패치됩니다.

트레잇은 두 모듈에 나뉘어 있습니다. `PartialEq`와 `PartialOrd`는 비교 연산자를 담당하므로 다른 연산자 트레잇과 함께 `rok::core::ops`에 있습니다([2.3](203-ops.md)). `Eq`, `Ord`, `Hash`, `Ordering`은 `rok::core::cmp`에 있습니다. `PartialEq`, `PartialOrd`, `Eq`, `Ord`, `Hash`, `Ordering`은 prelude에 있으므로([0.2.3](../000-meta/002-import.md)) 사용자 코드는 `use` 없이 이름으로 씁니다. `Hash` 구현이 써 넣는 해셔는 `rok::core::hash`에 있습니다([2.5.11](#2511-rokcorehash-해셔)).

Rok은 비교를 트레잇 4개의 위계(`PartialEq` / `Eq` / `PartialOrd` / `Ord`)와 별도의 `Hash` 트레잇으로 나눕니다. 이렇게 나누면 실용적인 요구 두 가지를 함께 만족합니다. 하나는 IEEE 754 부동소수의 NaN 처리이고, 다른 하나는 해시 일관성 보장입니다.

## 2.5.1. 트레잇 4개의 위계: partial이 필요한 이유

위계는 두 가지 관점으로 볼 수 있습니다.

**집합 관점**: `A ⊃ B`는 "A를 만족하는 타입의 집합이 B를 만족하는 타입의 집합을 포함"한다는 뜻입니다. A가 더 일반적이고 B가 더 구체적입니다.

```
PartialEq  ⊃  Eq           // PartialEq 인 타입의 집합 ⊇ Eq 인 타입의 집합
PartialOrd ⊃  Ord          //  (모든 Eq 는 PartialEq 이지만 그 역은 아님)
PartialEq  ⊃  PartialOrd
```

**함의 관점(상위 트레잇)**: `B ⇒ A`는 "B를 구현하면 A도 자동으로 요구된다"는 뜻입니다. Rok 코드로는 `trait B: A`로 적습니다. 이때 **A가 B의 상위 트레잇(supertrait)**입니다.

```rok
trait Eq: PartialEq { ... }                    // PartialEq 가 Eq 의 supertrait
trait PartialOrd: PartialEq { ... }            // PartialEq 가 PartialOrd 의 supertrait
trait Ord: PartialOrd + Eq { ... }             // PartialOrd 와 Eq 가 Ord 의 supertrait
```

두 관점은 같은 사실을 다른 각도에서 봅니다. `B ⇒ A`면 B인 타입은 모두 A이기도 하므로 `A ⊃ B`가 따라 나옵니다. 그래서 상위 트레잇은 집합 관점에서 "더 큰 쪽"입니다.

`Hash` 트레잇은 위 위계와 별개의 줄에 있습니다.

```
Eq ⊃ Hash         // Eq 인 타입 중 일부만 Hash. Hash 는 Eq 와의 일관성을 약속
```

부분(partial) 트레잇을 따로 두는 이유는 IEEE 754 부동소수의 NaN 때문입니다.

```rok
let a: f64 = 0.0 / 0.0;       // NaN
let b: f64 = 0.0 / 0.0;       // NaN
a == b;                       //→ false (NaN != NaN by IEEE 754)
a < b;                        //→ false
a > b;                        //→ false
a <= b;                       //→ false
```

NaN은 자기 자신과도 같지 않은 값입니다. 반사성(reflexivity)을 어기므로 `a == a`가 보장되지 않습니다. 그래서 타입마다 구현하는 트레잇이 갈립니다. `f32`와 `f64`는 **`PartialEq`, `PartialOrd`**만 구현합니다. `i32`, `bool`, `str` 등은 **`Eq`, `Ord`**까지 구현해 전순서를 만족합니다.

이렇게 나눈 덕분에 `Hash`, `Dict` / `Set`, 정렬 알고리듬에서 Hash의 일관성 약속과 전순서 보장이 안전하게 지켜집니다.

## 2.5.2. `PartialEq`: 부분 동등성(`==`, `!=`)

부분 동등성입니다.

```rok
#[lang("eq_trait")]
trait PartialEq<Rhs = Self> {
    #[infix("==")]
    fn eq(self, rhs: Rhs) -> bool;

    #[infix("!=")]
    fn ne(self, rhs: Rhs) -> bool {
        !self.eq(rhs)                // default impl
    }
}
```

Unicode 토큰 `≡`와 `≠`에는 따로 중위(infix) 바인딩이 없습니다. 렉서가 이 토큰을 `==`와 `!=`로 읽으므로([refs-lang 1.10.3](../../refs-lang/001-lexical/110-punctuation-and-operator-tokens.md#unicode-수학-연산자)) `eq`와 `ne`로 디스패치됩니다.

PartialEq의 **약속**은 대칭성(`a == b`와 `b == a`가 동치)과 추이성(`a == b`이고 `b == c`이면 `a == c`)입니다. 다만 반사성(`a == a`)은 IEEE 754 NaN 때문에 보장되지 않습니다.

### 기본 `ne`

`ne`의 기본 구현은 `!self.eq(rhs)`입니다. 성능 등을 이유로 따로 구현해도 됩니다.

### 사용 예

```rok
let r1 = 5i32 == 5i32;     //→ true
let r2 = "hi" != "hello";  //→ true

let nan: f64 = f64::NAN;
let r3 = nan == nan;       //→ false  (PartialEq 의 부분성)
```

## 2.5.3. `Eq`: 완전 동등성

완전 동등성은 마커 트레잇으로 정의합니다.

```rok
trait Eq: PartialEq<Self> {
    // marker trait: 추가 메서드 없음
}
```

`Eq`는 **마커 트레잇(marker trait)**입니다. 메서드는 없고 **반사성** 약속만 더합니다.

Eq가 더하는 **약속**은 반사성입니다. `a == a`가 늘 참이라는 뜻입니다. 이 약속이 있어야 `Dict` / `Set`의 키와 정렬 알고리듬이 제대로 동작합니다.

**구현 정책**은 이렇습니다. 정수, 진리값, 문자, 문자열 타입(`i32`, `i64`, `u8`..`u64`, `bool`, `char`, `c_char`, `str` 등)은 모두 `Eq`를 구현합니다. 부동소수 타입과 부동소수를 포함한 합 타입(`f32`, `f64`, `f64 | none` 등)은 `Eq`를 구현하지 않습니다. 사용자 struct나 enum에는 모든 필드가 `Eq`일 때만 `#[derive(Eq)]`를 쓸 수 있습니다.

```rok
let n: i32 = 42;
n == n;       //→ true (Eq 보장)
```

## 2.5.4. `PartialOrd`: 부분 순서(`<`, `>`, `<=`, `>=`)

부분 순서 트레잇은 비교 연산자를 정의합니다.

```rok
#[lang("cmp_trait")]
trait PartialOrd<Rhs = Self>: PartialEq<Rhs> {
    #[infix("<")]
    fn lt(self, rhs: Rhs) -> bool;

    #[infix(">")]
    fn gt(self, rhs: Rhs) -> bool;

    #[infix("<=")]
    fn le(self, rhs: Rhs) -> bool;

    #[infix(">=")]
    fn ge(self, rhs: Rhs) -> bool;

    fn partial_cmp(self, rhs: Rhs) -> Ordering | none {
        // default impl: lt/gt/le 조합
        if self.lt(rhs) { return Ordering::Less; }
        if self.gt(rhs) { return Ordering::Greater; }
        if self.le(rhs) { return Ordering::Equal; }
        none                              // NaN vs NaN 등: 비교 불가
    }
}
```

`≡`, `≠`와 마찬가지로 렉서는 `≤`와 `≥`를 `<=`와 `>=`로 읽습니다.

이 트레잇의 **약속**은 반대칭성(`a < b`이면 `!(b < a)`)과 추이성(정의된 비교에 한해 `a < b`이고 `b < c`이면 `a < c`)입니다. 삼분성은 부분적으로만 성립합니다. 두 값 사이의 순서가 늘 정의되지는 않고, NaN처럼 비교할 수 없는 값이 있습니다.

`partial_cmp`는 기본 구현이 있는(provided) 메서드이고 `Ordering | none`을 반환합니다. 비교할 수 없으면(NaN 등) `none`입니다.

### `Ordering` 타입

3방향 비교의 결과는 다음 enum입니다.

```rok
enum Ordering {
    Less,
    Equal,
    Greater,
}
```

`Ord::cmp`는 `Ordering`을 직접 반환합니다. `Ordering`은 `Clone`, `Copy`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`, `Hash`, `Debug`를 구현합니다(`Less` / `Equal` / `Greater`; `Less < Equal < Greater`). 고유 메서드는 다음과 같습니다.

```rok
impl Ordering {
    const fn is_lt(self) -> bool;        // self 가 Less
    const fn is_eq(self) -> bool;        // self 가 Equal
    const fn is_gt(self) -> bool;        // self 가 Greater
    const fn reverse(self) -> Ordering;  // Less 와 Greater 를 맞바꿈; Equal 은 그대로
}
```

```rok
let o = 3.cmp(7);     //→ Less
o.is_lt();            //→ true
o.reverse();          //→ Greater
```

### 비교 체인

[refs-lang 3.2.5](../../refs-lang/003-expressions/302-precedence-and-associativity.md#325-비교-체인)대로 방향이 같은 비교는 이어 쓸 수 있고, 각 피연산자는 한 번 평가합니다.

```rok
lo <= x < hi;     // lo <= x && x < hi
a < b > c;        // 컴파일 에러: 두 방향. a < b && b > c 로 적음
```

## 2.5.5. `Ord`: 완전 순서

완전 순서 트레잇입니다.

```rok
#[lang("ord_trait")]
trait Ord: Eq + PartialOrd<Self> {
    fn cmp(self, rhs: Self) -> Ordering;

    // default: Ord 가 정의된 두 값은 항상 비교 가능
    fn min(self, rhs: Self) -> Self {
        if self.le(rhs) { self } else { rhs }
    }

    fn max(self, rhs: Self) -> Self {
        if rhs.ge(self) { rhs } else { self }   // 같으면 rhs: 같은 값 중 마지막
    }

    #[track_caller]
    fn clamp(self, low: Self, high: Self) -> Self {
        if low.gt(high) { panic("Ord::clamp: low > high; pass the bounds in order, `x.clamp(low, high)`") }
        if self.lt(low) { low }
        else if self.gt(high) { high }
        else { self }
    }
}
```

Ord가 더하는 **약속**은 전체성입니다. 어떤 두 값 사이의 순서도 `Less`, `Equal`, `Greater` 중 하나로 정의됩니다. 그래서 `partial_cmp`는 `none`을 반환하지 않고 항상 `Ordering` 값을 돌려줍니다.

이 보장이 있어야 정렬 알고리듬이 제대로 동작합니다.

**구현 정책**: `i32`, `i64`, `u*`, `bool`, `char`, `c_char`, `str`은 `Ord`를 구현합니다. `f32`, `f64`는 NaN 때문에 비교할 수 없는 값이 있으므로 `Ord`를 구현하지 않습니다.

### `min` / `max` / `clamp`

기본 구현이 있는 메서드가 3개 있으므로 구현하는 쪽에서 따로 정의하지 않아도 쓸 수 있습니다. 두 값이 같으면 `min`은 `self`를, `max`는 `rhs`를 돌려줍니다. 그래서 같은 값 중 `min`은 처음 것을, `max`는 마지막 것을 남기며, `Iterator::min` / `max`와 같습니다([2.7](207-iter.md)). `clamp`는 `f64::clamp`처럼 `low > high`이면 panic이 일어납니다.

```rok
let r = 3i32.min(7i32);              //→ 3
let m = 5.max(10);                   //→ 10
let c = 100.clamp(0, 50);            //→ 50
let o = 1.0f64.cmp(2.0);             // ERROR: f64 는 Ord 가 정의되지 않음
let k = 1.0f64.clamp(0.0, 10.0);     //→ 1.0: Ord 가 아니라 고유 메서드 f64::clamp (2.1.4)
```

## 2.5.6. `Hash`: 해시(Eq 일관성 약속)

`Hash` 값은 자신을 `Hasher`([2.5.11](#2511-rokcorehash-해셔))에 써 넣고, `Hasher`는 받은 내용을 `u64` 하나로 만듭니다.

```rok
#[lang("hash_trait")]
trait Hash: Eq {
    fn hash<H: Hasher>(self, ref h: H);
}
```

**핵심 약속**은 다음과 같습니다.

> `a == b` ⇒ `a`와 `b`는 같은 쓰기 순서를 만들므로, 어느 해셔든 둘에 같은 해시를 냅니다

`Dict<K, V, S>`와 `Set<T, S>`의 모든 알고리듬은 이 약속이 있어야 정확합니다.

`Hash: Eq`이므로 Eq를 구현하지 않은 타입은 Hash도 구현할 수 없습니다. `f64`는 `Eq`를 구현하지 않으므로 `Hash`도 구현할 수 없습니다.

### 구현이 쓰는 것

구현은 자신의 부분을 정해진 순서로, 각 부분의 `hash`나 `Hasher`의 `write_<int>`로 씁니다. 길이가 정해지지 않은 값의 연속(리스트의 원소)은 `h.write_length_prefix(len)`으로 시작합니다. 이것이 없으면 이웃한 연속끼리 경계가 밀릴 수 있습니다. `[[1, 2], [3]]`과 `[[1], [2, 3]]`이 같은 쓰기를 만들게 됩니다. `write_str`은 그 자체로 접두 충돌이 없으므로 앞에 `write_length_prefix`를 쓰지 않습니다.

표준 구현이 쓰는 것은 다음과 같습니다.

| 타입 | 쓰는 것 |
|------|---------|
| `i*`, `u*` | `write_<type>(self)`. `usize` / `isize`는 모든 타깃에서 8바이트 |
| `bool` | `write_u8(0 / 1)` |
| `char` / `c_char` | `write_u32` / `write_u8` |
| `str` | `write_str(self)` |
| `List<T>` | `write_length_prefix(len)`, 그다음 각 원소 |
| `[T; N]` | 각 원소(`N`은 타입에 들어 있음) |
| 튜플 | 각 성분을 순서대로 |
| 합 `A \| B` | `write_usize(항 번호)`, 그다음 그 항의 `hash` |
| `NonZero` / `Positive` | 안의 값 |
| `NonNan` / `Finite` | 비트를 `write_u64`로. `-0.0`은 `0.0`으로 |
| `Int` | 부호, `write_length_prefix(limb 수)`, 그다음 32비트 limb. 한 값은 어느 표현이든 같게 씀 |
| `Dict<K, V, S>` / `Set<T, S>` | 원소마다 `RandomState::new()`의 해셔로 따로 해시해 결과를 (wrapping) 더한 뒤 `write_length_prefix(len)`과 `write_u64(합)` |

`Dict`와 `Set`은 비교할 때처럼 순서와 무관하게 해시합니다. 원소마다 `S`와 상관없이 프로세스 키를 쓰므로, 같은 두 dict는 `S`가 달라도 같은 해시를 냅니다.

### 해시 얻기

한 번에 부르는 형태는 없습니다. 해셔를 만들고, 쓰고, 끝냅니다.

```rok
use rok::core::hash::{BuildHasher, RandomState};

let h = RandomState::new().build_hasher();
"hello".hash(ref h);
let a = h.finish();       // 이번 실행 내내 "hello"에 같은 값
```

### 사용자 정의

```rok
#[derive(PartialEq, Eq, Hash)]
struct UserId { id: u64; }

// 자동 derive: 모든 필드 (id: u64) 가 Eq+Hash 라 가능
```

직접 쓴 구현은 동등성이 보는 것만 정확히 씁니다.

```rok
use rok::core::hash::Hasher;

struct Tag { name: str; }

impl PartialEq for Tag {
    fn eq(self, rhs: Tag) -> bool { self.name.to_lowercase() == rhs.name.to_lowercase() }
    fn ne(self, rhs: Tag) -> bool { !self.eq(rhs) }
}
impl Eq for Tag {}

impl Hash for Tag {
    fn hash<H: Hasher>(self, ref h: H) {
        h.write_str(self.name.to_lowercase());   // 같은 태그는 같은 것을 씀
    }
}
```

### 충돌(collision)

같은 타입의 서로 다른 두 값이 같은 해시를 내도 됩니다. `a != b`여도 그렇습니다. 버그가 아닙니다. 64비트 해시 공간에서는 충돌을 피할 수 없습니다. 충돌은 `Dict` 같은 자료구조가 처리합니다.

### 안정성

약속은 핵심 약속 하나뿐입니다. 해시 값은 같은 프로그램이라도 실행마다, 기계마다, Rok 버전마다 다를 수 있고, 구현이 하는 쓰기도 그렇습니다. 그러므로 프로그램은 해시를 저장하거나 다른 프로세스로 보내면 안 됩니다. 바뀌지 않아야 하는 해시는 `SipHasher13` / `SipHasher24`에 바이트와 정수를 직접 써서 얻습니다([2.5.11](#2511-rokcorehash-해셔)). `x.hash(ref h)`로 얻지 않습니다. `Dict`와 `Set`은 기본으로 `RandomState`로 해시합니다. 그 키는 프로세스마다 한 번 무작위로 뽑으므로 키가 표의 어느 칸에 놓이는지는 실행마다 다릅니다. 반면 순회하고 출력하는 순서는 삽입 순서이므로 달라지지 않습니다([2.9.3](209-collections.md)).

## 2.5.7. 구현 매트릭스

타입별 트레잇 구현은 다음과 같습니다.

| 타입             | PartialEq                  | Eq  | PartialOrd | Ord | Hash | 동작                          |
|------------------|----------------------------|-----|------------|-----|------|-------------------------------|
| `i*`, `u*`       | ✓                          | ✓   | ✓          | ✓   | ✓    | `rok.eq.OP`, `rok.lt.OP`, ... |
| `f32`, `f64`     | ✓                          | ✗   | ✓          | ✗   | ✗    | `rok.eq.f64`, `rok.lt.f64`    |
| `bool`           | ✓                          | ✓   | ✓          | ✓   | ✓    | `rok.eq.bool` (`<`는 일반 본문) |
| `char`, `c_char` | ✓                          | ✓   | ✓          | ✓   | ✓    | `rok.eq.char`, ...            |
| `str`            | ✓                          | ✓   | ✓          | ✓   | ✓    | 사전식                        |
| `Tuple<...>`     | ✓ (모든 부분 PartialEq 시) | ✓   | ✓          | ✓   | ✓    | 사전식, 1~12항                |
| `[T; N]`         | ✓ (T:PartialEq)            | ✓   | ✓          | ✓   | ✓    | 사전식                        |
| `List<T>`        | ✓ (T:PartialEq 시)         | ✓   | ✓          | ✓   | ✓    | 사전식                        |
| `Dict<K,V,S>`    | ✓ (K:Hash, V:PartialEq)    | ✓ (V:Eq) | ✗     | ✗   | ✓ (V:Hash) | 순서 무관 비교 / 해시   |
| `Set<T,S>`       | ✓ (T:Hash)                 | ✓   | ✗          | ✗   | ✓    | 순서 무관 비교 / 해시         |
| `Range<T>`       | ✓ (T:PartialEq)            | ✓ (T:Eq) | ✗     | ✗   | ✓ (T:Hash) | start/end 비교          |
| 합 `A \| B`      | ✓ (모든 항이 구현 시)      | ✓   | `T \| none`만 | `T \| none`만 | ✓ | `none` 먼저 → 페이로드 |

`Dict`와 `Set`은 순서 없는 컨테이너이므로 `PartialOrd` / `Ord`가 없습니다. `Dict`와 `Set`의 모든 구현은 키(집합 원소)가 `Hash`여야 합니다. `Set<T, S>`는 `T: Hash`이면 항상 `PartialEq`, `Eq`, `Hash`입니다. `K: Hash`인 `Dict<K, V, S>`는 `V: PartialEq`이면 `PartialEq`, `V: Eq`이면 `Eq`, `V: Hash`이면 `Hash`입니다. 모든 `S: BuildHasher`에서 그렇습니다. 동등성은 `S`를 보지 않습니다. 둘 다 순회 순서와 무관하게 비교하고 해시합니다([2.9](209-collections.md)).

`List`는 사전식으로 비교합니다. 앞에서부터 원소를 비교해 처음 다른 원소가 순서를 정합니다. 한쪽이 다른 쪽의 접두사이면 짧은 쪽이 작습니다.

순서가 있는 합은 `none` 말고 항이 하나 이하인 합뿐입니다([refs-lang 2.6.4](../../refs-lang/002-types/206-sum-types.md#264-집합-의미론)). `T | none`은 `T`가 `PartialOrd` / `Ord`이면 같은 트레잇을 구현합니다. Rust나 Haskell처럼 `none`은 어떤 `T` 값보다 작고, 두 `T` 값은 `T`의 순서로 비교합니다. `min` / `max` / `clamp`도 같은 순서를 따릅니다. `none` 말고 항이 둘 이상인 합(`i32 | str`)에는 `PartialOrd` / `Ord`가 없습니다. 이런 값을 비교하거나 정렬하면 컴파일 에러이므로 키를 정해 정렬합니다(`sort_by_key`, `sort_by`, `min_by_key`).

## 2.5.8. broadcast 비교 트레잇

[2.6 broadcast](206-broadcast.md)의 브로드캐스트 트레잇 20개 중 비교 트레잇 6개입니다.

```rok
trait DotEq<Rhs>  { #[infix(".==")] fn dot_eq(...) -> Output; }
trait DotNe<Rhs>  { #[infix(".!=")] fn dot_ne(...) -> Output; }
trait DotLt<Rhs>  { #[infix(".<")] fn dot_lt(...) -> Output; }
trait DotGt<Rhs>  { #[infix(".>")] fn dot_gt(...) -> Output; }
trait DotLe<Rhs>  { #[infix(".<=")] fn dot_le(...) -> Output; }
trait DotGe<Rhs>  { #[infix(".>=")] fn dot_ge(...) -> Output; }
```

각 트레잇은 List나 Vec3 같은 컨테이너를 원소별로 비교합니다. 결과 타입(`Output`)은 보통 `List<bool>` 또는 `[bool; N]`입니다.

브로드캐스트 의미 전체는 [2.6 broadcast](206-broadcast.md)에 있습니다.

## 2.5.9. `#[derive(Eq, Ord, Hash, ...)]`

[refs-lang 6.2 `#[derive]`](../../refs-lang/006-meta-system/602-built-in-attributes.md)가 derive 메커니즘을 정의합니다. cmp 트레잇 5개는 모두 derive로 구현할 수 있습니다.

```rok
#[derive(PartialEq, Eq, PartialOrd, Ord, Hash)]
struct Version { major: u32; minor: u32; patch: u32; }
```

derive 동작은 트레잇마다 다릅니다. `PartialEq`와 `Eq`는 모든 필드 동등성의 AND입니다. `PartialOrd`와 `Ord`는 필드 선언 순서를 따라 사전식으로 비교합니다. `Hash`는 필드 선언 순서대로 각 필드의 `hash`를 씁니다. 열거형은 먼저 variant 번호를 `write_usize`로 씁니다. variant가 하나뿐인 열거형은 쓰지 않습니다. 정확한 쓰기는 안정하지 않습니다([2.5.6](#256-hash-해시eq-일관성-약속)).

모든 필드가 (재귀적으로) 같은 트레잇을 구현해야 합니다. `Eq` / `Ord`는 상위 트레잇(`PartialEq` / `PartialOrd`, `Eq`)도 함께 derive로 구현하거나 직접 구현해야 합니다. 한 필드라도 `Eq`를 구현하지 않으면 `#[derive(Eq)]`는 컴파일 에러입니다.

## 2.5.10. 패턴 매칭과 cmp

`match` 가지의 리터럴 패턴은 `PartialEq::eq`를 씁니다.

```rok
match x {
    0 => "zero",
    1 => "one",
    _ => "other",
}
// → 0.eq(x) → 비교, 1.eq(x) → 비교, ...
```

범위 패턴(`0..=10 =>`)은 `PartialOrd::le`와 `ge`를 씁니다.

패턴 의미 전체는 [refs-lang 3.11 패턴](../../refs-lang/003-expressions/311-patterns.md)에 있습니다.

## 2.5.11. `rok::core::hash`: 해셔

이 모듈에는 `Hash` 구현이 써 넣는 대상이 있습니다. 이 모듈은 prelude에 없으므로 사용자 코드는 이름을 쓰는 항목을 가져옵니다(`hash<H: Hasher>` 구현에는 `use rok::core::hash::Hasher;`, 그 밖에는 `use rok::core::hash::{BuildHasher, RandomState};`). 값에 `Hasher` 메서드를 호출할 때(`h.write_str(..)`)는 다른 `rok::` 트레잇처럼 `use`가 필요 없습니다.

```rok
trait Hasher {
    fn write<B: AsBytes>(ref self, bytes: B);   // 바이트 그대로: 길이도 끝 표시도 없음
    fn finish(self) -> u64;                    // 지금까지의 해시. 상태는 그대로

    // 기본 구현: 정수의 little-endian 바이트
    fn write_u8(ref self, x: u8);
    fn write_u16(ref self, x: u16);
    fn write_u32(ref self, x: u32);
    fn write_u64(ref self, x: u64);
    fn write_usize(ref self, x: usize);        // 모든 타깃에서 8바이트
    fn write_i8(ref self, x: i8);              // .. write_i16 / i32 / i64 / isize도 부호 없는 쪽처럼
    fn write_length_prefix(ref self, len: usize);   // write_usize(len)
    fn write_str(ref self, s: str);            // write_length_prefix(len), 그다음 바이트
}

trait BuildHasher {
    type Hasher: Hasher;
    fn build_hasher(self) -> Self::Hasher;
}

struct RandomState { /* 프로세스 키 */ }
impl RandomState { fn new() -> RandomState; }
impl BuildHasher for RandomState { type Hasher = DefaultHasher; }

struct DefaultHasher { /* .. */ }
struct BuildHasherDefault<H> {}                // H::default()를 만듦
impl<H: Hasher + Default> BuildHasherDefault<H> { const fn new() -> BuildHasherDefault<H>; }   // Default 도 구현
impl<H: Hasher + Default> BuildHasher for BuildHasherDefault<H> { type Hasher = H; }

struct SipHasher13 { /* .. */ }
struct SipHasher24 { /* .. */ }
impl SipHasher13 { const fn with_keys(k0: u64, k1: u64) -> SipHasher13; }
impl SipHasher24 { const fn with_keys(k0: u64, k1: u64) -> SipHasher24; }
```

- **`RandomState`**는 128비트 키를 가집니다. 프로그램이 처음 키를 찾을 때 운영체제의 난수원에서 뽑습니다. 한 프로세스의 `RandomState::new()`는 모두 같은 키를 가지므로, 키가 같은 두 dict는 같은 해셔를 씁니다. `Copy`, `Eq`, `Default`이고, `Debug`는 키를 보여 주지 않습니다. `Dict`와 `Set`의 기본 `S`입니다([2.9.3](209-collections.md#293-dictk-v-s-해시-맵)).
- **`DefaultHasher`**는 `RandomState`의 해셔입니다. 알고리듬(지금은 SipHash-1-3)과 그 출력은 사양이 정하지 않으며 어느 릴리스에서든 바뀔 수 있습니다. 이 해셔의 `write_str`은 길이 대신 바이트 뒤에 `0xFF` 한 바이트를 씁니다. UTF-8에는 이 바이트가 나오지 않습니다.
- **컴파일 시점에 만든 `RandomState`**(`const`, 또는 상수 평가 중에 만든 값)는 모두 0인 키를 가집니다. 런타임은 이 키를 뽑지 않습니다. 런타임에서 이 값은 프로세스 키를 뜻합니다. 상수 평가 중에 이 키로 해시한 표는 런타임에 처음 쓸 때 프로세스 키로 한 번 다시 해시합니다.
- **`BuildHasherDefault<H>`**는 해시마다 `H::default()`를 만듭니다. 호출자의 해셔를 쓰는 `Dict` / `Set`(`Dict<K, V, BuildHasherDefault<Fnv>>`)에 씁니다. 키 없는 고정 해셔는 빠르지만, 키를 고를 수 있는 사람은 키끼리 충돌하게 만들 수 있습니다. 키가 공격자에게서 올 수 없을 때만 쓰십시오. 더 빠른 해셔는 stone이 제공합니다.
- **`Debug`**: `DefaultHasher`, `SipHasher13`, `SipHasher24`, `BuildHasherDefault<H>`는 타입 이름만 출력하고 상태는 출력하지 않습니다(`SipHasher13 { .. }`). 그래서 키가 로그에 남지 않습니다.
- **`SipHasher13` / `SipHasher24`**는 호출자의 키로 쓰는 SipHash-1-3과 SipHash-2-4입니다. 써 넣은 바이트에 대한 출력은 참조 SipHash와 같고 릴리스와 타깃이 바뀌어도 그대로입니다. `write_<int>`는 정수의 little-endian 바이트를, `write_usize`는 그 8바이트를 씁니다. 안정한 것은 프로그램이 직접 쓴 바이트와 정수뿐입니다. `Hash` 구현의 쓰기는 안정하지 않으므로([2.5.6](#256-hash-해시eq-일관성-약속)), 샤딩 키처럼 저장하는 해시는 `x.hash(ref h)`로 얻지 않습니다.

```rok
use rok::core::hash::SipHasher13;

fn shard(user: str, shards: u64) -> u64 {
    let h = SipHasher13::with_keys(0x5eed, 0);
    h.write(user);                // 바이트만: 안정함
    h.finish() % shards
}
```

암호학적 강도가 필요하면 `rok::core::crypto`(SHA-2, SHA-3)를 쓰십시오.
