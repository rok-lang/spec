# 2.19. par - 병렬 처리 API

`rok::core::par` 모듈은 데이터 병렬 처리 API입니다. 설계는 Rust의 Rayon을 참고했으며, `task::*`와 같은 work-stealing 스케줄러 위에서 동작합니다.

`use rok::core::**;`가 묵시적으로 적용되므로 `par::for_each`, `par::map` 등은 import 없이 바로 쓸 수 있습니다. 모듈 prefix `par::`는 그대로 남습니다. 병렬 처리 의도를 눈에 띄게 드러내야 하는 자리에서는 `use rok::core::par::*;`를 명시적으로 적기를 권장합니다.

## 2.19.1. 핵심 API

핵심 API는 함수 여섯 개입니다.

```rok
fn for_each<I: IntoIterator<Item = T>, T: Send>(iter: I, f: fn(T) + Send + Sync);
fn map<I: IntoIterator<Item = T>, T: Send, U: Send>(iter: I, f: fn(T) -> U + Send + Sync) -> List<U>;
fn reduce<T: Send + Sync>(iter: List<T>, init: T, f: fn(T, T) -> T + Send + Sync) -> T;
fn filter<T: Send>(iter: List<T>, pred: fn(T) -> bool + Send + Sync) -> List<T>;
fn join<T1: Send, T2: Send>(f1: fn() -> T1 + Send, f2: fn() -> T2 + Send) -> (T1, T2);    // 2 개 병렬
fn scope(f: fn(Scope));                                          // 동적 spawn
```

`for_each` / `map` / `reduce` / `filter`의 `f`는 여러 worker가 동시에 부르므로 `+ Send + Sync`입니다.

- `for_each` / `map` / `filter`는 입력 순서를 보존합니다. `map` / `filter`의 결과 `List`는 입력과 같은 순서입니다.
- `for_each` / `map` / `filter`는 항목마다 worker에 줍니다. 두 항목이 `Sync`가 아닌 컬렉션 하나에 닿으면 안 됩니다 ([2.13.9](213-marker.md#2139-send--sync---스레드-경계-marker)). 호출마다 먼저 두 항목에서 함께 닿는 컬렉션이 있는지 찾습니다. 넘김(hand-off)의 복사처럼 항목의 구성 요소와 컬렉션의 원소를 깊이와 상관없이 따라가되, plain 값 (수, `bool`, `str`)의 컬렉션 안으로는 들어가지 않습니다. 그런 컬렉션을 찾으면 항목들을 호출한 스레드에서 하나씩 차례로 실행합니다. 그래서 경쟁이 없고, 제자리에서 바꾼 내용은 worker로 돌릴 때와 똑같이 남습니다. 이때 경고가 호출 위치를 알려 줍니다 (위치마다 한 번). slice는 읽기만 합니다. 어느 항목도 리스트 자체를 들고 있지 않다면, 항목들은 한 리스트를 그 slice (큰 리스트 하나의 조각)로 공유해도 됩니다. slice가 닿는 원소는 하나씩 따라갑니다. 검사 비용은 항목이 닿는 컬렉션마다 객체 header에 표시하는 만큼입니다 (리스트 하나짜리 항목은 컬렉션마다 약 15 ns, 중첩된 항목은 약 50 ns이며 대부분 메모리 읽기입니다. 컬렉션이 없는 항목은 비용이 없습니다). 일이 적은 작은 항목이 많으면 검사 비용이 일보다 클 수 있습니다. 경고는 대신 쓸 코드를 알려 줍니다. 항목마다 자기 값을 주거나 (공유하는 값은 저장하기 전에 `.clone()`), 읽기만 하는 데이터는 검사가 따라가지 않는 `Frozen` (2.16.4b)이나 다른 `Sync` 타입으로 공유하면 됩니다. 항목 가운데 future는 그 frame으로 봅니다. 그래서 future 하나를 든 두 항목도 하나씩 실행합니다. `par`는 항목을 넘기지 않으므로, frame이 컬렉션을 캡처하는 future는 항목이 될 수 없습니다 (컴파일 에러). 그런 future는 task로 spawn합니다 ([2.18.1](218-task.md#2181-핵심-api)). `filter`의 결과는 입력의 항목을 공유합니다.
- `reduce`는 입력을 chunk로 나눠 chunk마다 병렬로 접은 뒤, `init`과 chunk 결과들을 순서대로 접습니다. 입력이 비어 있으면 `init`을 돌려줍니다.
- `scope` 안에서 spawn한 자식은 scope가 끝날 때 모두 join됩니다.
- `par`는 task와 같은 work-stealing pool ([2.18.3](218-task.md#2183-스케줄러-모델---work-stealing)) 위에서 실행됩니다. `par` 안에서 기다리는 worker는 그동안 다른 task를 실행하므로, task 안에서 `par`를 불러도 deadlock이 생기지 않습니다. `scope`에 넘기는 `Scope`와 그 핸들은 다음과 같습니다.

```rok
struct Scope { /* scope 안의 작업 목록 */ }
impl Scope {
    fn spawn<T: Send>(self, f: fn() -> T + Send) -> ScopeHandle<T>;
}

struct ScopeHandle<T> { /* spawn 된 작업 하나 */ }
impl<T> ScopeHandle<T> {
    fn join(self) -> T;          // 그 작업이 끝날 때까지 기다림
}
```

`scope`가 끝날 때 join되지 않은 작업도 모두 기다립니다.

```rok
par::scope(|s| {
    let left = s.spawn(|| sum_range(0, 500));
    let right = s.spawn(|| sum_range(500, 1000));
    println(f"{left.join() + right.join()}");   // join 은 그 작업이 끝날 때까지 기다림
    s.spawn(|| log("background"));                    // join 하지 않음. scope 가 끝날 때 기다림
});
```

### 사용 예


```rok
use rok::core::par::*;

let xs: List<i32> = (0..1000).collect();

par::for_each(xs, |x| { process(x) });

let squared: List<i32> = par::map(xs, |x| x * x);

let total: i32 = par::reduce(squared, 0, |a, b| a + b);

let (a, b) = par::join(
    || compute_a(),
    || compute_b(),
);

par::scope(|s| {
    for chunk in chunks {
        s.spawn(|| process_chunk(chunk));
    }
});           // ← scope 끝에서 모든 spawn 완료 보장
```

## 2.19.2. `par::for_each` vs Iterator

순차 처리와 병렬 처리는 호출 형태로 구분됩니다.

```rok
xs.into_iter().for_each(f);     // 순차 (single thread)
par::for_each(xs, f);            // 병렬 (worker pool)
```

작업은 chunk 단위로 데이터 병렬 분배되며, 작업량이 고르지 않은 unbalanced workload도 work-stealing 스케줄러가 자동으로 고르게 맞춥니다.

## 2.19.3. `par::scope` - 구조적 병렬

`par::scope`는 동적으로 작업을 spawn할 수 있는 구조적 병렬 API입니다.

```rok
par::scope(|s| {
    let h1 = s.spawn(|| task1());
    let h2 = s.spawn(|| task2());
    // h1, h2 결과 사용 가능 (scope 안에서)
    // scope 끝에서 자동 join
});
```

structured concurrency 형태를 따릅니다. scope는 spawn한 자식이 모두 끝날 때까지 block합니다.

### `par::try_scope` - 첫 에러에서 취소

에러를 던지는 자식을 두려면 `try_scope`를 씁니다.

```rok
fn try_scope<E: Send>(f: fn(TryScope<E>) throws (E)) throws (E);

impl<E: Send> TryScope<E> {
    fn spawn<T: Send>(self, f: fn() throws (E) -> T + Send) -> TryScopeHandle<T, E>;
    fn is_cancelled(self) -> bool;
}

impl<T, E: Send> TryScopeHandle<T, E> {
    fn join(self) throws (E) -> T;     // 자기 에러, 또는 시작 전에 취소됐으면 scope 의 첫 에러
}
```

자식 하나가 에러를 던지면 scope가 취소됩니다. 아직 시작하지 않은 자식은 실행되지 않고, 이미 실행 중인 자식은 끝까지 실행됩니다. 모든 자식이 끝나면 `try_scope`가 그 첫 에러를 다시 던집니다. 실행 중인 자식은 `is_cancelled()`를 보고 일찍 끝낼 수 있습니다.

```rok
try par::try_scope(|s| {
    let a = s.spawn(|| try load("a"));
    let b = s.spawn(|| try load("b"));
    use_both(try a.join(), try b.join());
});
```

## 2.19.4. `par::reduce` - 결합 법칙 요구

`par::reduce`의 시그니처는 다음과 같습니다. 쓸 때는 몇 가지 수학적 조건이 따릅니다.

```rok
fn reduce<T: Send + Sync>(iter: List<T>, init: T, f: fn(T, T) -> T + Send + Sync) -> T;
```

결합 함수 `f`가 결합 법칙(associative)을 만족해야 결과가 결정론적입니다. `init`은 가능하면 **identity**로 두기를 권장합니다. `+`라면 0, `*`라면 1입니다. 부동소수점 합산처럼 큰 값이 누적되는 비결합 함수는 **결과가 비결정적**일 수 있으므로 따로 주의해야 합니다.

```rok
let sum: i64 = par::reduce([1, 2, 3, 4, 5], 0, |a, b| a + b);    //→ 15

// 부동소수점: 결과 약간 다를 수 있음
let total: f64 = par::reduce(values, 0.0, |a, b| a + b);
```

## 2.19.5. `par::join` - 정확히 2 개

작업 두 개를 동시에 실행하고 결과 쌍을 받으려면 `par::join`을 씁니다.

```rok
let (a, b) = par::join(
    || expensive_computation_1(),
    || expensive_computation_2(),
);
```

작업 두 개는 fork-join에서 가장 흔한 형태라 전용 함수를 둡니다. 작업이 N개라면 `par::for_each`나 `par::scope`를 씁니다.

## 2.19.6. SIMD / GPU 통합

`par` 모듈은 CPU 데이터 병렬을 중심에 둡니다. SIMD multiversioning은 `par::map` 안에서 target_feature에 따라 자동으로 적용됩니다. GPU 가속은 표준 라이브러리에 속하지 않으며, 라이브러리가 `rok::bare::mlir` ([1.9](../100-bare/109-mlir.md))로 다룹니다.

```rok
par::map(xs, |x| heavy_op(x));     // CPU work-stealing + SIMD 자동
```

## 2.19.7. 모듈 매핑

각 API의 모듈 위치와 내부 전략은 다음과 같습니다.

| 항목            | 모듈            | 전략                      |
|-----------------|-----------------|---------------------------|
| `par::for_each` | `rok::core::par` | chunk + work-steal        |
| `par::map`      | `rok::core::par` | parallel collect          |
| `par::reduce`   | `rok::core::par` | tree reduction            |
| `par::filter`   | `rok::core::par` | parallel collect 후 dedup |
| `par::join`     | `rok::core::par` | 2-task work-steal         |
| `par::scope`    | `rok::core::par` | spawn handle + auto-join  |

내부적으로는 `task::spawn` 위에 한 겹을 얹은 구조이며, 같은 스케줄러를 공유합니다.
