# 9.6. JIT 엔진

이 절은 REPL과 Jupyter가 쓰는 JIT 실행 엔진을 정의합니다. [실행 엔진과 사용자 표면](../000-meta/001-execution-modes.md)에서 정한 JIT 엔진의 구현입니다. 셀 세션의 규칙은 [9.7.0](907-jit-cells.md#970-셀-세션의-규칙)이 정합니다.

## 9.6.1. 구조: rokc와 JIT 호스트

세션은 별도의 **호스트 프로세스**(host process)에서 실행됩니다. 호스트 프로세스는 런타임을 담고 세션이 끝날 때까지 삽니다. 호스트는 `rokc`와 함께 미리 빌드하고 내장 lld로 링크합니다. 호스트는 libLLVM이나 ORC 없이 셀 오브젝트를 직접 로드합니다.

```
rokc (front end)                         JIT host (세션 동안 하나)
  셀 → parse → HIR → MIR                     librokr.a 전체
     → native backend                        런타임 초기화는 한 번
     → 기계어 + relocation  ─────────────►   실행 가능 메모리에 로드, 심볼 해소
                                             → 셀 진입 함수를 한 번 실행
```

- 셀은 [9.2.10](902-aot-pipeline.md#9210-백엔드-선택)의 백엔드 선택을 따릅니다. `-O0`에서 셀은 호스트가 매핑하고 링크하는 네이티브 오브젝트([9.2.11](902-aot-pipeline.md#9211-네이티브-백엔드))이고 LLVM을 쓰지 않습니다. `-O0`보다 높은 수준의 코드와 네이티브 백엔드가 맡지 않는 코드(`__mlir_op`, 그 밖의 타깃)는 내장 MLIR → LLVM 파이프라인으로 오브젝트를 만듭니다. 이 오브젝트도 같은 실행 가능 메모리에 로드합니다.
- 호스트는 코드를 실행 가능 메모리에 놓고 재배치(relocation)를 런타임, libc, 앞 셀의 심볼로 해소합니다. 그런 다음 셀의 진입 함수를 한 번 실행합니다.
- 호스트는 런타임(`librokr.a`)의 모든 심볼을 내보냅니다. 셀 코드는 런타임과 libc 심볼을 호스트 프로세스에서 찾습니다.

## 9.6.2. 코드 로드

셀은 오브젝트 파일입니다. `-O0`에서는 네이티브 백엔드가, 그보다 높으면 LLVM이 컴파일합니다. 셀 코드는 재배치 정보가 있는 위치 독립 코드입니다. 호스트는 세션마다 심볼 테이블을 하나 둡니다. 셀을 로드하면 셀의 정의를 이 테이블에 더합니다. 해소할 수 없는 심볼이 있으면 셀은 실패하고, 에러가 그 심볼 이름을 알립니다([9.7](907-jit-cells.md)).

## 9.6.3. 심볼과 재정의

한 세션은 심볼 테이블 하나를 씁니다. 모든 셀의 정의가 여기에 쌓입니다.

- 셀이 이미 정의된 심볼을 다시 정의하면 호스트는 새 정의의 이름을 `<name>.r<cell>`로 바꿉니다. 이후 셀의 참조는 가장 새 이름에 링크됩니다.
- 재정의는 다음 셀부터 효력이 있습니다([9.7.0](907-jit-cells.md#970-셀-세션의-규칙) 규칙 3).
- `rokc`는 재정의된 심볼에 의존하는 함수를 다시 컴파일합니다. 그래서 재정의 전에 컴파일한 코드도 이후 셀에서 다시 닿으면 새 정의를 씁니다. 재정의된 `f`를 부르는 `g`가 그런 예입니다.
- 셀 코드와 옛 정의는 세션이 끝날 때까지 해제하지 않습니다.

## 9.6.4. 라이브러리 코드의 재사용

표준 라이브러리와 의존 패키지의 코드는 세션에 한 번만 컴파일합니다.

- `rokc`는 호스트가 이미 로드한 함수와 그 MIR을 기억합니다. 셀의 함수가 이미 로드된 함수와 같으면 코드 대신 참조만 넘깁니다.
- MIR이 같으면 뜻도 같도록 셀 사이의 이름을 고정합니다. 문자열 리터럴 전역은 내용 해시로 이름을 짓습니다. GC 타입 id는 [ScanTable](../008-abi/802-scan-table.md) 내용을 키로 삼아 세션 동안 고정합니다.
- 이 셀이 새로 정의하는 것(바뀐 함수, `static`, 바인딩 슬롯)을 직접 또는 간접으로 부르는 함수는 다시 컴파일합니다.
- 셀의 오브젝트에는 셀이 더하는 것만 들어갑니다. 새로 정의하는 함수와, 그 코드가 읽는 이전 셀 static의 초기화 가드입니다. 그 코드가 가리키는 심볼만 이름으로 부릅니다.

## 9.6.5. 실행 흐름(REPL 한 줄 / Jupyter 한 셀)

```
1. rokc: 입력 → parse → HIR (에러면 셀을 버림, 세션 상태 그대로)
2. rokc: 셀 → MIR → native backend → 기계어
         (이미 로드된 함수는 참조로, 재정의는 새 이름으로)
3. host: 세션 스냅샷을 fork 한 프로세스에서 코드를 로드하고 셀을 한 번 실행
4. 성공: 그 프로세스가 새 스냅샷이 됨. 값이 있으면 `타입: 값` 출력
   실패 (panic, 종료, 시그널, 로드 실패): 이전 스냅샷이 이어받음 (9.7.0 규칙 5)
```

Unix에서는 3단계에서 fork로 프로세스를 복제합니다. fork가 없는 호스트(Windows)는 셀을 실행하기 전에 세션의 메모리와 스레드를 저장하고, 셀이 실패하면 되돌려 놓습니다. 관찰되는 결과는 fork한 스냅샷과 같습니다.

셀 하나의 지연은 약 0.1초이고 대부분 프런트엔드에서 걸립니다(참고값).

## 9.6.6. JIT와 AOT의 차이

| 측면        | JIT (REPL / Jupyter)                         | AOT                               |
|-------------|----------------------------------------------|-----------------------------------|
| 파이프라인  | rok-mir까지 같음                            | 같음                              |
| 백엔드      | 네이티브, 호스트에 로드                     | 네이티브(`-O0`) 또는 MLIR → LLVM, 그 뒤 lld |
| 단위        | 셀 (라이브러리는 세션에 한 번)               | 패키지                            |
| 결과        | 호스트 메모리                                  | 실행 파일 / `.a`                  |

두 엔진은 같은 단형화와 rok-mir를 공유하고 두 백엔드가 같은 ABI를 따릅니다. 그래서 의미가 같습니다.
