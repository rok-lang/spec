# 9.7. JIT 셀 실행 흐름과 상태 관리

이 절에서는 [JIT 엔진](906-jit-engine.md) 이 사용자 입력 (cell) 을 어떻게 처리하는지 자세히 정의합니다.

## 9.7.0. 셀 세션의 규칙

다음은 셀 세션이 지키는 규칙입니다. 구현은 [9.6 JIT 엔진](906-jit-engine.md) 입니다.

1. **한 번만 실행.** 각 셀의 코드는 정확히 한 번 실행됩니다. 앞 셀의 부수 효과 (I/O, 시각, 난수) 는 되풀이되지 않습니다.
2. **상태 유지.** 셀 최상위의 `let` 바인딩, `static` 의 상태, `any` 값 (`any Tr` 포함) 은 이후 셀로 이어집니다. 바인딩은 대입할 수 있고, 같은 이름의 재 `let` 은 새 바인딩으로 가립니다 (9.7.3).
3. **항목 유지와 재정의.** `fn` / `struct` / `impl` 등 항목은 유지됩니다. 같은 항목을 다시 정의하면 다음 셀부터 새 정의가 쓰입니다. 재정의 전에 컴파일된 코드도 이후 셀이 다시 닿으면 새 정의를 씁니다 (재정의된 `f` 를 부르는 `g` 는 새 `f` 를 부름). `static` 을 다시 정의하면 그 상태는 새로 시작합니다. 타입이 재정의된 바인딩은 더 이상 쓸 수 없으며, 쓰려 하면 그 사실을 note 로 알려 줍니다.
4. **`any` 의 정체성.** `any` 의 타입 tag 는 한 세션의 모든 셀에서 같습니다. 앞 셀에서 넣은 `any` 값을 뒤 셀에서 `is` / 패턴으로 꺼낼 수 있습니다.
5. **실패한 셀.** panic 하거나 프로세스를 끝내거나 죽은 셀은 바인딩에 부분 효과를 남기지 않습니다. 세션은 그 셀 이전의 상태로 계속됩니다. 이미 일어난 외부 효과 (I/O 등) 는 되돌리지 않습니다. 이전 셀의 스레드: 실패한 셀 뒤에 세션은 원래 자리로 돌아온 스레드만 (Windows), 또는 아무것도 (fork host) 남기지 않습니다. 런타임은 자기 executor 스레드를 다시 시작하며, 사라진 사용자 스레드를 join 하면 잃었다고 보고합니다 (`JoinError` 코드 `JOIN_LOST`, [stdlib 3.4](../../refs-standard-libraries/300-std/304-thread.md)). 세션은 조용한 순간에 저장합니다: poll 중인 task 도, 실행 중인 blocking job 도 없을 때입니다 (host 는 셀 전에 그것들을 기다리며, 그 기다림을 인터럽트하면 셀이 취소됨). 그래서 task 와 job 을 잃는 일은 없습니다. 사라진 스레드가 block 중에 가진 lock 은 해제됩니다.
6. **표시.** 식 셀은 값을 `Display` 로 출력하고, 뒤에 `?` 를 붙이면 `Debug` 로 출력합니다. 요청한 트레잇 (평범한 식엔 `Display`, 뒤에 `?` 를 붙이면 `Debug`) 이 없는 값은 타입 이름만 출력합니다 (9.7.7).

다음 바인딩과 효과는 다룰 수 없습니다.

- 최상위에서 이름을 적을 수 없는 타입 (클로저, 비공개 타입 등) 의 바인딩. 만드는 셀에서 거부합니다.
- 셀 안의 `exit(..)` 호출. 그 셀은 실패한 셀로 다룹니다 (규칙 5). (단독 `exit` 나 `quit` 는 세션을 끝냅니다, [9.9.9](909-debug-tools.md#999-repl--jupyter-디버그).)
- 실패한 셀이 띄운 스레드. 그 셀 뒤에 남지 않습니다 (규칙 5).

## 9.7.1. Cell 의 종류

REPL 의 한 줄과 Jupyter 의 한 셀은 그 내용에 따라 처리 방식이 달라집니다.

```
1. expression                → evaluate + bind as `it` + print
2. statement (let / call)    → execute (return value is unit)
3. definition (fn / struct)  → add to the session's items
4. import (use / mod)        → update the session's visible names
5. meta / attribute          → handle as appropriate
```

다섯 가지 모두 같은 cell 처리 흐름을 따르며, 마지막 출력만 달라집니다. 식 셀이 보여 준 값은 이후 셀을 위해 `it` 에 바인딩합니다 (9.7.7). 식 셀은 값을 (`Display` 로) 출력하고, `let` 셀은 아무것도 출력하지 않습니다. divergent 식 셀 ([4.3.7](../004-functions/403-return.md#437-divergent-함수); `panic(..)`, `exit(..)`, `throw`) 은 문으로 실행합니다.

셀은 암묵 `main` 처럼 top-level 문에서 `await` 할 수 있습니다 ([4.16.5](../004-functions/416-entry-point.md#4165-비동기-main)). 그러면 셀은 끝날 때까지 executor 위에서 실행됩니다. 그 셀의 `let` 바인딩과 값은 다른 셀과 똑같이 이후 셀로 이어집니다.

> [!IMPORTANT]
> 언어 의미론의 관점에서 셀의 연속은 암묵 `main.rok` 의 끝에 top-level 문과 항목을 덧붙이는 것과 같습니다 ([4.16.10](../004-functions/416-entry-point.md#41610-jit--repl-과의-관계)). 셀의 `let` 은 암묵 `main` 의 지역 변수이므로 이후 셀의 문에서는 보이지만, 셀에서 선언한 `fn` 본체에서는 보이지 않습니다. 아래 9.7.3 의 global 저장은 셀 경계를 넘어 지역 변수를 유지하기 위한 구현 방식이며, 이 가시성 규칙을 바꾸지 않습니다. 셀 최상위의 같은 이름 재 `let` (9.7.3), 셀 재실행 (9.7.4), 마지막 식 값의 자동 표시와 그 바인딩 `it` (9.7.7) 은 세션 조작으로서 대화형 표면에만 있습니다.

## 9.7.2. 실행 흐름: 자세히

```
1. parse → AST                      (에러: 표시, 셀을 버림)
2. HIR 로 낮춤, 타입 검사           (에러: 표시, 셀을 버림)
3. MIR → native 기계어              (재사용 / 재정의 처리, 9.6.3 / 9.6.4)
4. host: 스냅샷을 fork 한 프로세스에서 로드, 셀 진입 함수 실행
5. 성공: 새 스냅샷, 바인딩과 항목을 세션에 반영, 결과 출력
   실패: 이전 스냅샷으로 계속, 에러 표시
```

각 단계는 transactional 하게 동작하며, 실패하면 직전 상태로 롤백됩니다.

모든 셀은 `/dev/null` (Windows 에서는 `NUL`) 을 표준 입력으로 받아 실행하므로, stdin 을 읽는 셀은 입력의 끝을 봅니다. REPL host 는 사용자 환경과 상관없이 런타임을 시작하기 전에 `ROK_GC_CONCURRENT=off` 로 설정합니다. 동시 mark 스레드는 스냅샷에 들어가지 않으므로, 세션의 full 수집은 그 스레드 없이 mark 합니다 ([7.5](../007-runtime/705-concurrent-collection.md)).

## 9.7.3. Top-level 변수 저장

REPL 과 Jupyter 의 셀 사이에서 변수가 공유되어야 하므로, top-level 변수는 세션이 유지되는 동안 계속 살아 있어야 합니다.

```rok
[1] let x = 42i32;
[2] let y = x + 1;       // 이전 x 사용
```

### 저장 형태

```
let x = 42                  → global of the inferred type (i32)
let x: i64 = 42             → global of the written type (i64)
heap payload                → register GC root
                             (compiler-emitted shadow stack frame,
                              linked into rokr shadow stack chain)
```

각 top-level 변수는 host 에 그 타입 (적었거나 추론한 타입) 의 export 된 global 로 저장됩니다. 다음 cell 이 같은 변수를 참조할 때는 그 global 주소를 통해 찾아갑니다.

### GC root 등록

heap 객체를 가리키는 top-level 변수는 GC 가 root 로 추적해야 하므로, [shadow stack](../000-meta/007-glossary.md#shadow-stack) 체인에 이어 둡니다.

자세한 메커니즘은 [배리어와 루트 추적](../007-runtime/704-barriers-and-roots.md) 의 shadow stack 부분을 참조합니다.

### 같은 이름의 재선언

```rok
[1] let x = 1i32;            // x: i32
[2] let x = "hi";            // 셀 최상위의 재선언: 새 바인딩 (x: str)
```

[변수 선언](../005-modules/501-variable-declaration.md#514-같은-스코프-내-재선언-금지) 에서 같은 스코프 안의 재선언은 ERROR 로 처리됩니다. 그러나 셀을 고쳐 다시 실행하는 흐름을 지원하기 위해, REPL 과 Jupyter 셀의 최상위에서는 같은 이름을 다시 `let` 으로 선언할 수 있습니다. 재선언은 새 바인딩을 만들며, 새 바인딩의 타입은 이전 바인딩과 달라도 됩니다. 이후 셀은 새 바인딩을 봅니다. 이 예외는 셀 최상위에만 적용되며, 셀 안의 블록이나 일반 소스 파일에는 적용되지 않습니다.

이때 기존 global 은 덮어쓰며, 메모리는 그대로 둔 채 이름 자리만 새 정의를 가리키도록 바꿉니다.

이러한 동작 덕분에 "아, 이 변수를 다시 정의해야겠다" 와 같은 REPL 의 자연스러운 사용 패턴이 매끄럽게 지원됩니다.

## 9.7.4. Undo / 셀 재실행

### Jupyter 의 셀 재실행

Jupyter 에서 셀을 고쳐 다시 실행하면 새 셀로 실행됩니다. 그 셀이 다시 정의한 항목과 바인딩은 이후 셀부터 새 것이 쓰입니다 (9.7.0 규칙 2, 3). 앞서 실행된 셀의 효과를 지우지는 않습니다.

### Undo 의 의미

REPL 에는 명시적인 undo 가 없으며, 마지막 cell 을 그대로 덮어쓰거나 새 cell 을 추가하면서 작업을 진행합니다.

Jupyter 에서도 셀을 지우거나 다시 실행해 앞 셀의 효과를 되돌리지는 않습니다. 처음 상태로 돌아가려면 세션을 다시 시작합니다 (REPL 의 `:reset`).

## 9.7.5. 에러 모드

### 셀 컴파일 에러

```
parse error / type error / 의미 에러.
  - cell 추가하지 않음.
  - 세션의 바인딩과 항목은 그대로.
  - 이미 컴파일된 함수의 재사용 정보는 유지.
  - 사용자에게 에러 표시.
```

이 단계는 완전한 transactional 동작을 보장하므로, 에러가 발생하기 직전의 상태가 그대로 유지됩니다. 셀을 컴파일하다가 rokc 자신이 panic 해도 (internal compiler error), `rokc lsp`, `rokc repl`, `rokc jupyter` 는 이것을 견딥니다: language server 는 분석한 버퍼의 에러 진단으로 보고하고, REPL / kernel 은 그 셀을 실패시킵니다. 둘 다 계속 서비스합니다.

### 셀 런타임 에러

```
실행 중 panic / 잡히지 않은 throw / 프로세스 종료 / 세그폴트.
  - cell 은 추가하지 않음. 바인딩과 항목은 그 셀 이전 상태 그대로.
  - 사용자에게 에러 표시.
  - 다음 cell 진행 가능.
```

바인딩과 항목은 셀 이전 상태로 돌아가지만 (9.7.0 규칙 5), 이미 일어난 외부 효과 (출력, 파일 쓰기 등) 는 되돌리지 않습니다. 실패한 셀을 세션에 남기지 않으므로, 고친 셀을 다시 입력하면 됩니다. fork 가 없는 host (Windows) 는 셀 전에 세션의 메모리와 스레드를 저장하고 셀이 실패하면 되돌려 놓으며, 관찰되는 결과는 fork 한 스냅샷과 같습니다.

### JIT 실패

host 가 셀의 코드를 로드하거나 링크하지 못하면 (알 수 없는 `extern` 심볼 등) 셀 런타임 에러와 같이 다룹니다. 셀을 실행한 fork 프로세스가 끝나고 이전 스냅샷이 이어받습니다.

### 위치

셀 안의 진단과 panic 위치는 셀 자신의 텍스트 기준 `<repl>:line:col` 로 표시합니다.

## 9.7.6. 캐시

한 세션 안에서는 host 가 이미 컴파일한 함수를 재사용합니다 (9.6.4). 세션을 넘는 디스크 캐시는 없습니다.

## 9.7.7. 시각화 / 출력

### REPL 출력

```
>>> 1 + 2
3
>>> "hi"
hi
```

마지막 식의 값을 `Display` 로 자동 출력합니다. 뒤에 `?` (`xs?`) 를 붙이면 `Debug` 로, `:type xs` 는 타입만 출력합니다. 요청한 트레잇 (평범한 식엔 `Display`, `?` 엔 `Debug`) 이 없는 값은 타입 이름만 출력하고, `let` 셀은 아무것도 출력하지 않습니다.

```
>>> let xs = [1, 2, 3];
>>> xs
List<i32>
>>> xs?
[1, 2, 3]
```

### `it`: 마지막으로 보여 준 값

식 셀이 보여 준 값은 `it` 에 바인딩합니다. `it` 은 다른 것과 같은 세션의 top-level 바인딩이므로, 이후 셀이 읽고 대입할 수 있고 `:vars` 가 나열합니다. 아무것도 보여 주지 않는 셀 (문, unit 값, 실패한 셀) 은 `it` 을 그대로 두며, 최상위에서 이름을 적을 수 없는 타입의 값도 마찬가지입니다 (9.7.0).

```
> 2 + 3
5
> it * 10
50
> it
50
```

사용자가 정의한 이름이 우선합니다. 셀이 `let` 으로 `it` 을 바인딩하거나 `it` 이라는 항목을 정의하면, 그 뒤 식 셀은 `:reset` 전까지 `it` 을 바인딩하지 않습니다. Jupyter 세션에서도 같습니다.

### Jupyter 출력

각 cell 의 결과는 `text/plain` 항목 하나만 담은 `execute_result` 로 보내며, 그 내용은 REPL 이 출력하는 텍스트와 같습니다. 다른 MIME 타입은 만들지 않습니다.

자세한 Jupyter 통합 내용은 [Jupyter 통합](908-jupyter-integration.md) 에서 정의합니다.

## 9.7.8. 입력 단위: REPL 식별

REPL 은 완성된 식이나 문장 단위로 입력을 처리합니다.

```
>>> 1 + 2
3
>>> let x =
... 42i32;          (continued input)
>>> x
42
```

프롬프트는 `>>>` 이고, 셀이 이어지는 동안은 `...` 입니다. 셀은 줄 끝에서 끝나며 토큰으로 판정합니다. 괄호, 문자열, 블록 주석이 아직 열려 있거나, 마지막 토큰이 문장을 끝낼 수 없거나 (이항 연산자, `.`, `,`, `=`, `->`, `|`, 또는 `else` · `in` 같은 키워드), 입력이 본체 없는 항목 머리로 끝나면 (`fn g(x: i32)` 다음 줄에 `-> i32 { .. }`) `...` 로 입력을 계속 받습니다. 문자 리터럴, 문자열, 주석 안의 괄호는 세지 않습니다. 그 밖의 줄은 셀을 끝냅니다. `///` 문서 주석 줄도 입력을 이어 받습니다: 그 주석은 다음 줄들의 항목에 속합니다. `:` 로 시작하는 줄은 명령이며 그 줄에서 끝납니다. 셀의 마지막 top-level 문이 `;` 없는 `let` 이나 대입이면 (`let x = 1`, `k += 2` 처럼) `;` 을 보충합니다. `let` 은 그대로 바인딩하고 셀은 아무것도 표시하지 않습니다. 다른 문은 바꾸지 않으며, 진단은 셀을 입력한 그대로 인용합니다. 터미널에서는 앞선 출력이 줄바꿈으로 끝나지 않았더라도 각 프롬프트가 새 줄에서 시작하고, 파이프 입력에는 프롬프트를 출력하지 않습니다. 끝나지 않은 셀 안에서 표준 입력이 끝나면, 그 셀은 실행하지 않고 에러를 보고하며 `rokc repl` 은 1 로 종료합니다. 실패한 셀은 종료 코드를 바꾸지 않습니다.

## 9.7.9. 입력 단위: Jupyter 셀

Jupyter 의 한 셀은 여러 줄로 구성된 입력이며, 한 번에 모두 처리됩니다.

```
[Cell 1]:
let x = 42i32;
let y = x * 2i32;
y                       # 마지막 식 = cell 결과
```

cell 의 마지막 식이 곧 cell 의 결과가 되며, 그 외의 부분은 사이드 이펙트 (정의나 호출) 로 처리됩니다.

## 9.7.10. 프로그램 로드 (`repl <path>`)

프로그램 경로를 준 `rokc repl <path>` 는 프로그램을 새 세션에 로드한 뒤, 그 세션에서 REPL 을 이어 갑니다. 라이브러리 패키지 경로를 주면 그 패키지를 의존성으로 붙이고 `use <name>::*;` 를 첫 셀로 실행하며 (`:reset` 뒤에도 다시), 그 밖에는 아무것도 로드하지 않습니다.

- **먼저 검사.** 무엇이든 실행하기 전에 프로그램 전체를 검사합니다. 에러는 파일 자신의 위치로 보고하며, 아무것도 실행하지 않고 빈 세션으로 시작합니다.
- **항목.** 항목과 import 는 세션에 들어갑니다.
- **문.** top-level 문은 셀로 실행합니다. 각 셀은 top-level `let` (또는 마지막 문) 에서 끝납니다.
- **실패.** panic, `exit()`, 빠져나간 에러가 나면, 끝난 셀의 바인딩은 그 셀이 끝난 시점의 값을 유지하고 실패한 구간의 대입은 사라집니다. 프로그램의 나머지는 실행하지 않으며 세션은 이어집니다.
- **쓸 수 없는 바인딩.** 이후 셀이 쓸 수 없는 바인딩 (비공개 또는 이름을 적을 수 없는 타입) 은 이후 문이 그 이름을 쓰지 않으면 버리고, 쓰면 마지막 사용까지의 문을 한 셀로 실행합니다.
- **`fn main`.** `fn main` 이 있는 프로그램은 `main` 을 진입점으로 실행하고, 그 뒤 `main` 은 세션에서 빠지므로 그 지역 변수는 보이지 않습니다.
- **위치.** 진단과 panic 은 파일 자신의 위치를 씁니다.
- **입력.** 프로그램의 stdin 은 `/dev/null` 입니다.
- **`:load`, `:reload`.** `:load <file>` 은 같은 규칙으로 실행 중인 세션에 프로그램을 로드하며, 그 항목은 세션의 같은 이름 항목을 대신합니다. `:reload` 는 마지막으로 로드한 프로그램을 다시 로드합니다 ([9.9.9](909-debug-tools.md#999-repl--jupyter-디버그)).
