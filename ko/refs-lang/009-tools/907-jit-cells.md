# 9.7. JIT 셀 실행 흐름과 상태 관리

이 절은 [JIT 엔진](906-jit-engine.md)이 사용자 입력인 셀(cell)을 처리하는 방식을 정의합니다.

## 9.7.0. 셀 세션의 규칙

다음은 셀 세션이 지키는 규칙입니다. 구현은 [9.6 JIT 엔진](906-jit-engine.md)입니다.

1. **한 번만 실행.** 각 셀의 코드는 정확히 한 번 실행됩니다. 앞 셀의 부수 효과(I/O, 시각, 난수)는 되풀이되지 않습니다.
2. **상태 유지.** 셀 최상위의 `let` 바인딩, `static`의 상태, `any` 값(`any Tr` 포함)은 이후 셀로 이어집니다. 바인딩에는 대입할 수 있습니다. 같은 이름으로 다시 `let`을 쓰면 새 바인딩이 이전 바인딩을 가립니다(9.7.3).
3. **항목 유지와 재정의.** `fn` / `struct` / `impl` 등 항목은 유지됩니다. 같은 항목을 다시 정의하면 다음 셀부터 새 정의를 씁니다. 재정의 전에 컴파일된 코드도 이후 셀에서 다시 닿으면 새 정의를 씁니다. 재정의된 `f`를 부르는 `g`는 새 `f`를 부릅니다. `static`을 다시 정의하면 그 상태는 새로 시작합니다. 타입이 재정의된 바인딩은 더 이상 쓸 수 없습니다. 쓰려고 하면 note로 그 사실을 알립니다.
4. **`any`의 정체성.** `any`의 타입 태그는 한 세션의 모든 셀에서 같습니다. 앞 셀에서 넣은 `any` 값을 뒤 셀에서 `is` / 패턴으로 꺼낼 수 있습니다.
5. **실패한 셀.** panic이 일어나거나, 프로세스를 끝내거나, 죽은 셀은 바인딩에 부분 효과를 남기지 않습니다. 세션은 그 셀 이전의 상태로 계속됩니다. 이미 일어난 외부 효과(I/O 등)는 되돌리지 않습니다. 이전 셀의 스레드는 다음과 같이 됩니다. 실패한 셀 뒤에 세션은 원래 자리로 돌아온 스레드만 남기거나(Windows) 아무 스레드도 남기지 않습니다(fork 호스트). 런타임은 자기 executor 스레드를 다시 시작합니다. 사라진 사용자 스레드를 기다리면(join) 스레드를 잃었다고 보고합니다(`JoinError` 코드 `JOIN_LOST`, [stdlib 3.4](../../refs-standard-libraries/300-std/304-thread.md)). 세션은 조용한 순간에 저장합니다. 폴링 중인 task도, 실행 중인 블로킹 작업도 없을 때입니다. 호스트는 셀을 실행하기 전에 이들이 끝나기를 기다립니다. 기다리는 중에 인터럽트하면 셀이 취소됩니다. 그래서 task와 작업을 잃는 일은 없습니다. 사라진 스레드가 블록된 채 쥐고 있던 락은 해제됩니다.
6. **표시.** 식 셀은 값을 `타입: 값`(Debug) 형식으로 출력합니다. `Debug`가 없으면 타입만 출력합니다(9.7.7).

다음 바인딩과 효과는 다룰 수 없습니다.

- 최상위에서 이름을 적을 수 없는 타입(클로저, 비공개 타입 등)의 바인딩. 바인딩을 만드는 셀에서 거부합니다.
- 셀 안의 `exit()`. 그 셀은 실패한 셀로 다룹니다(규칙 5).
- 실패한 셀이 띄운 스레드. 그 셀 뒤에 남지 않습니다(규칙 5).

## 9.7.1. 셀의 종류

REPL의 한 줄과 Jupyter의 한 셀은 내용에 따라 다르게 처리합니다.

```
1. expression                → evaluate + store last_value + print
2. statement (let / call)    → execute (return value is unit)
3. definition (fn / struct)  → add to the session's items
4. import (use / mod)        → update the session's visible names
5. meta / attribute          → handle as appropriate
```

다섯 가지 모두 같은 셀 처리 흐름을 따르고 마지막 출력만 다릅니다. 식 셀은 `타입: 값`을 출력하고, `let` 셀은 아무것도 출력하지 않습니다. 발산하는 식 셀(`panic(..)`, `exit(..)`, `throw`)은 문으로 실행합니다.

> [!IMPORTANT]
> 언어 의미론으로 보면 셀을 잇따라 실행하는 것은 암묵 `main.rok`의 끝에 최상위 문과 항목을 덧붙이는 것과 같습니다([4.16.10](../004-functions/416-entry-point.md#41610-jit--repl과-관계)). 셀의 `let`은 암묵 `main`의 지역 변수입니다. 그래서 이후 셀의 문에서는 보이지만 셀에서 선언한 `fn` 본체에서는 보이지 않습니다. 아래 9.7.3의 전역 저장은 셀 경계를 넘어 지역 변수를 유지하는 구현 방식일 뿐이고, 이 가시성 규칙을 바꾸지 않습니다. 다음은 세션 조작이므로 대화형 표면에만 있습니다. 셀 최상위에서 같은 이름으로 다시 하는 `let`(9.7.3), 셀 재실행(9.7.4), 마지막 식 값의 자동 표시(9.7.7)입니다.

## 9.7.2. 실행 흐름: 자세히

```
1. parse → AST                      (에러: 표시, 셀을 버림)
2. HIR 로 낮춤, 타입 검사           (에러: 표시, 셀을 버림)
3. MIR → native 기계어              (재사용 / 재정의 처리, 9.6.3 / 9.6.4)
4. host: 스냅샷을 fork 한 프로세스에서 로드, 셀 진입 함수 실행
5. 성공: 새 스냅샷, 바인딩과 항목을 세션에 반영, 결과 출력
   실패: 이전 스냅샷으로 계속, 에러 표시
```

각 단계는 트랜잭션처럼 동작합니다. 실패하면 직전 상태로 롤백합니다.

## 9.7.3. 최상위 변수 저장

REPL과 Jupyter의 셀은 변수를 공유해야 합니다. 그래서 최상위 변수는 세션이 이어지는 동안 살아 있어야 합니다.

```rok
[1] let x = 42i32;
[2] let y = x + 1;       // 이전 x 사용
```

### 저장 형태

```
untyped (let x = 42)        → global of {tag:u32, payload:i64}
typed (let x: i32 = 42i32)  → global of that type
heap payload                → register GC root
                             (compiler-emitted shadow stack frame,
                              linked into rokr shadow stack chain)
```

최상위 변수는 각각 호스트의 전역으로 저장됩니다. 이후 셀이 같은 변수를 참조하면 그 전역의 주소로 찾습니다.

### GC 루트 등록

힙 객체를 가리키는 최상위 변수는 GC가 루트로 추적해야 합니다. 그래서 이런 변수를 [shadow stack](../000-meta/007-glossary.md#shadow-stack) 체인에 이어 둡니다.

자세한 메커니즘은 [배리어와 루트 추적](../007-runtime/704-barriers-and-roots.md)의 shadow stack 부분에 있습니다.

### 같은 이름의 재선언

```rok
[1] let x = 1i32;            // x: i32
[2] let x = "hi";            // 셀 최상위의 재선언 - 새 바인딩 (x: str)
```

[변수 선언](../005-modules/501-variable-declaration.md#514-같은-스코프-내-재선언-금지)에 따르면 같은 스코프 안의 재선언은 에러입니다. 그러나 셀을 고쳐 다시 실행할 수 있도록 REPL과 Jupyter 셀의 최상위에서는 같은 이름을 `let`으로 다시 선언할 수 있습니다. 재선언은 새 바인딩을 만듭니다. 새 바인딩의 타입은 이전 바인딩과 달라도 됩니다. 이후 셀은 새 바인딩을 봅니다. 이 예외는 셀 최상위에만 적용됩니다. 셀 안의 블록이나 일반 소스 파일에는 적용되지 않습니다.

이때 기존 전역은 덮어씁니다. 메모리는 그대로 두고 이름 자리만 새 정의를 가리키도록 바꿉니다.

그래서 REPL에서 흔히 하듯 변수를 다시 정의할 수 있습니다.

## 9.7.4. Undo / 셀 재실행

### Jupyter의 셀 재실행

Jupyter에서 셀을 고쳐 다시 실행하면 새 셀로 실행됩니다. 그 셀이 다시 정의한 항목과 바인딩은 이후 셀부터 새것을 씁니다(9.7.0 규칙 2, 3). 앞서 실행된 셀의 효과를 지우지는 않습니다.

### Undo의 의미

REPL에는 따로 되돌리기(undo) 기능이 없습니다. 마지막 셀을 덮어쓰거나 새 셀을 더하면서 작업합니다.

Jupyter에서도 셀을 지우거나 다시 실행한다고 앞 셀의 효과가 되돌려지지는 않습니다. 처음 상태로 돌아가려면 세션을 다시 시작합니다(REPL의 `:reset`).

## 9.7.5. 에러 모드

### 셀 컴파일 에러

```
parse error / type error / 의미 에러.
  - cell 추가하지 않음.
  - 세션의 바인딩과 항목은 그대로.
  - 이미 컴파일된 함수의 재사용 정보는 유지.
  - 사용자에게 에러 표시.
```

이 단계는 완전히 트랜잭션처럼 동작하므로 에러 직전의 상태가 그대로 유지됩니다. 셀을 컴파일하다가 rokc 자신에서 panic이 일어나도(내부 컴파일러 에러) `rokc lsp`, `rokc repl`, `rokc jupyter`는 이를 견딥니다. 언어 서버는 분석한 버퍼의 에러 진단으로 보고하고, REPL과 커널은 그 셀을 실패로 처리합니다. 둘 다 서비스를 계속합니다.

### 셀 런타임 에러

```
실행 중 panic / 잡히지 않은 throw / 프로세스 종료 / 세그폴트.
  - cell 은 추가하지 않음 - 바인딩과 항목은 그 셀 이전 상태 그대로.
  - 사용자에게 에러 표시.
  - 다음 cell 진행 가능.
```

바인딩과 항목은 셀 이전 상태로 돌아갑니다(9.7.0 규칙 5). 하지만 이미 일어난 외부 효과(출력, 파일 쓰기 등)는 되돌리지 않습니다. 실패한 셀은 세션에 남지 않으므로 고친 셀을 다시 입력하면 됩니다. fork가 없는 호스트(Windows)는 셀을 실행하기 전에 세션의 메모리와 스레드를 저장하고, 셀이 실패하면 되돌려 놓습니다. 관찰되는 결과는 fork한 스냅샷과 같습니다.

### JIT 실패

호스트가 셀의 코드를 로드하거나 링크하지 못하면(알 수 없는 `extern` 심볼 등) 셀 런타임 에러와 같이 다룹니다. 셀을 실행한 fork 프로세스가 끝나고 이전 스냅샷이 이어받습니다.

### 위치

셀 안의 진단과 panic 위치는 셀 자신의 텍스트를 기준으로 `<repl>:line:col`로 표시합니다.

## 9.7.6. 캐시

한 세션 안에서는 호스트가 이미 컴파일한 함수를 재사용합니다(9.6.4). 세션을 넘는 디스크 캐시는 없습니다.

## 9.7.7. 시각화 / 출력

### REPL 출력

```
> 1 + 2
i32: 3
> [1, 2, 3]
List<i32>: [1, 2, 3]
```

마지막 식의 값과 타입을 `타입: 값` 형식으로 자동 출력합니다. 값은 `Debug`로 형식화합니다. `Debug`를 구현하지 않은 타입이면 타입만 출력합니다.

```
> let xs = [1, 2, 3];
> xs
List<i32>: [1, 2, 3]
```

### Jupyter 출력

각 셀의 결과는 Jupyter의 display protocol로 내보냅니다.

- 단순 값은 문자열로 나타냅니다.
- 컬렉션은 표나 JSON으로 나타냅니다.
- 이미지나 그래프는 라이브러리가 `Display::display_jupyter` 같은 훅으로 내보냅니다.

Jupyter 통합은 [Jupyter 통합](908-jupyter-integration.md)이 자세히 정의합니다.

## 9.7.8. 입력 단위: REPL 식별

REPL은 완성된 식이나 문장 단위로 입력을 받습니다.

```
> 1 + 2
i32: 3
> let x =
... 42i32;          (continued input)
> x
i32: 42
```

식이나 블록이 닫히지 않았으면 `...` 프롬프트를 표시하고 입력을 계속 받습니다. 끝나지 않은 셀 안에서 표준 입력이 끝나면 그 셀은 실행하지 않습니다. 에러를 보고하고 `rokc repl`은 1로 종료합니다. 실패한 셀은 종료 코드를 바꾸지 않습니다.

## 9.7.9. 입력 단위: Jupyter 셀

Jupyter의 한 셀은 여러 줄로 된 입력이고, 한 번에 모두 처리합니다.

```
[Cell 1]:
let x = 42i32;
let y = x * 2i32;
y                       # 마지막 식 = cell 결과
```

셀의 마지막 식이 셀의 결과입니다. 나머지는 부수 효과(정의나 호출)로 다룹니다.

## 9.7.10. 프로그램 로드(`repl <path>`)

프로그램 경로를 준 `rokc repl <path>`는 프로그램을 새 세션에 로드하고 그 세션에서 REPL을 이어 갑니다. 라이브러리 패키지 경로를 주면 그 패키지를 의존성으로 붙이고 `use <name>::*;`를 첫 셀로 실행합니다(`:reset` 뒤에도 다시 실행). 그 밖에는 아무것도 로드하지 않습니다.

- **먼저 검사.** 무엇이든 실행하기 전에 프로그램 전체를 검사합니다. 에러가 있으면 파일 자신의 위치로 보고하고, 아무것도 실행하지 않은 빈 세션으로 시작합니다.
- **항목.** 항목과 가져온 이름(import)은 세션에 들어갑니다.
- **문.** 최상위 문은 셀로 실행합니다. 각 셀은 최상위 `let`(또는 마지막 문)에서 끝납니다.
- **실패.** panic, `exit()`, 빠져나간 에러가 나면 끝난 셀의 바인딩은 그 셀이 끝난 시점의 값을 유지합니다. 실패한 구간의 대입은 사라집니다. 프로그램의 나머지는 실행하지 않고 세션은 이어집니다.
- **쓸 수 없는 바인딩.** 이후 셀이 쓸 수 없는 바인딩(비공개 타입이나 이름을 적을 수 없는 타입)이 있습니다. 이후 문이 그 이름을 쓰지 않으면 바인딩을 버립니다. 쓰면 마지막 사용까지의 문을 한 셀로 실행합니다.
- **`fn main`.** `fn main`이 있는 프로그램은 `main`을 진입점으로 실행합니다. 그 뒤 `main`은 세션에서 빠지므로 그 지역 변수는 보이지 않습니다.
- **위치.** 진단과 panic은 파일 자신의 위치를 씁니다.
- **입력.** 프로그램의 stdin은 `/dev/null`입니다.
