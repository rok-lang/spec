# 3.3. 브로드캐스트 연산자

[구두점과 연산자 토큰](../001-lexical/110-punctuation-and-operator-tokens.md)에서 정의한 점-접두 연산자(`.+`, `.*`, `.==` 등)는 원소별 연산(broadcast)에 쓰는 별도 토큰입니다. 일반 연산자처럼 트레잇 메서드 호출로 풀리지만, 대응하는 트레잇은 따로 있습니다.

## 3.3.1. 풀어 쓰기 패턴

점-접두 연산자는 다음과 같이 풀립니다.

```
a .+ b      →   <typeof(a) as DotAdd<typeof(b)>>::dot_add(a, b)
a .* b      →   <typeof(a) as DotMul<typeof(b)>>::dot_mul(a, b)
a .== b     →   <typeof(a) as DotEq<typeof(b)>>::dot_eq(a, b)
```

[연산자 디스패치](301-operator-dispatch.md)에서 다룬 일반 매핑과 형태가 같고, 대상 트레잇만 다릅니다. 점-접두 연산자는 이름이 **Dot**으로 시작하는 별도의 트레잇 패밀리에 대응합니다. 대응 관계는 다음과 같습니다.

| 점-접두 토큰 | 점 없는 형태      | 점-접두 트레잇  |
|--------------|-------------------|-----------------|
| `.+`         | `+` ↔ `Add`       | `DotAdd`        |
| `.-`         | `-` ↔ `Sub`       | `DotSub`        |
| `.*`         | `*` ↔ `Mul`       | `DotMul`        |
| `./`         | `/` ↔ `Div`       | `DotDiv`        |
| `.%`         | `%` ↔ `Rem`       | `DotRem`        |
| `.%%`        | `%%` ↔ `Modulo`   | `DotModulo`     |
| `.==`        | `==` ↔ `Eq`       | `DotEq`         |
| `.!=`        | `!=` ↔ `Ne`       | `DotNe`         |
| `.<`         | `<` ↔ (`Cmp::lt`) | `DotLt`         |
| `.>`         | `>`               | `DotGt`         |
| `.<=`        | `<=`              | `DotLe`         |
| `.>=`        | `>=`              | `DotGe`         |
| `.&&`        | `&&` (단축 평가)  | `DotLogicalAnd` |
| `.\|\|`        | `\|\|` (단축 평가)  | `DotLogicalOr`  |
| `.&`         | `&`               | `DotBitAnd`     |
| `.\|`         | `\|`               | `DotBitOr`      |
| `.^`         | `^`               | `DotBitXor`     |
| `.<<`        | `<<`              | `DotShl`        |
| `.>>`        | `>>`              | `DotShr`        |

이 트레잇의 정확한 시그니처와 이를 구현하는 타입은 표준 라이브러리가 정의합니다. 이 문서는 언어가 점-접두 토큰을 별도의 트레잇 패밀리로 풀어 쓴다는 사실만 다룹니다.

> [!IMPORTANT]
> **점-접두 논리 연산자에는 단축 평가가 없음**: `.&&`, `.||`는 점 없는 형태와 달리 단축 평가를 하지 **않습니다**. 브로드캐스트는 융합된 루프로 변환되므로 양쪽 피연산자를 항상 평가합니다. 의미로는 bool 컨테이너의 원소별 논리 결합입니다. 부작용이 있는 함수 호출은 어느 쪽 피연산자에 두든 항상 실행됩니다.

## 3.3.2. 우선순위와 결합성

점-접두 연산자의 우선순위와 결합성은 대응하는 점 없는 연산자와 같습니다.

```
a .+ b .* c     →   a .+ (b .* c)              // .* 가 .+ 보다 강함 (* > + 와 동일)
a .+ b .+ c     →   (a .+ b) .+ c              // 좌결합
```

## 3.3.3. 함수와 메서드 브로드캐스트

함수나 메서드 뒤에 `.`을 붙이면 그 함수나 메서드를 모든 원소에 적용합니다.

```rok
sin.(x)            // x 의 각 원소에 sin 적용
f64::sqrt.(arr)    // 메서드 형태도 가능
g.(a, b)           // 여러 인자
```

이 형태는 일반 함수나 메서드 호출의 결과를 모든 원소에 매핑한 새 컬렉션을 반환합니다. 표준 라이브러리의 `Iterator::map` 호출(또는 동등한 트레잇)로 풀립니다.

```
f.(x)        →   x.map(f)
g.(a, b)     →   a.zip(b).map(|(x, y)| g(x, y))
```

함수와 메서드 브로드캐스트에는 전용 트레잇이 없습니다. 반복자 변환을 줄여 쓴 형태입니다. 이 점이 이항 점-접두 연산자와 다릅니다.

## 3.3.4. 자동 루프 융합

컴파일러는 연속된 점-접두 표현식을 커널 하나로 융합할 수 있습니다.

```
sin.(a) .+ cos.(b) .* 2.0f64
```

가능하면 중간 배열을 만들지 않고 한 번의 순회로 결과를 만듭니다.

[컴파일 파이프라인](../000-meta/002-pipeline.md)의 MLIR 단계가 인접한 점-접두 체인을 linalg 연산 하나로 인식하므로 융합할 수 있습니다. SIMD와 GPU도 같은 메커니즘으로 쓸 수 있습니다.

융합 여부는 컴파일러의 분석에 달려 있고, 사양은 보장하지 않습니다. 대부분 융합된다는 실용적인 약속입니다.

## 3.3.5. 일반 연산자와 다른 의미

> [!IMPORTANT]
> 점-접두 연산자를 별도의 트레잇으로 둔 이유는 같은 자료에 수학적으로 다른 의미를 둘 수 있기 때문입니다.

```
m * n           // 행렬 곱 (Mul 구현, 사용자 정의)
m .* n          // 원소별 곱 (Hadamard product, DotMul)
```

NumPy의 `*`가 암묵적으로 원소별 연산이 되어 생긴 혼동을 피하려고, Rok은 두 의미를 항상 눈에 보이게 구분합니다.

이 구분은 [언어와 표준 라이브러리의 경계](../000-meta/004-language-vs-standard-libraries.md)에서 제시한 "구문은 언어, 의미는 라이브러리" 원칙을 그대로 적용한 결과입니다. 서로 다른 두 의미에 서로 다른 두 구문이 대응합니다.

## 3.3.6. 사용자 정의 트레잇 구현

타입에 점-접두 연산을 주려면 일반 연산자와 같은 방식으로 **Dot** 트레잇 패밀리를 구현하면 됩니다.

```rok
impl DotAdd for MyVector {
    type Output = MyVector;
    fn dot_add(self, rhs: MyVector) -> MyVector { ... }
}
```

새 트레잇이나 매크로를 더하지 않고 이 패턴만으로 점-접두 연산을 지원합니다.
