# 6.6. `#[keyword(...)]` 매직

`#[keyword("name")]` 속성은 표준 라이브러리가 새 키워드를 등록하는 메커니즘이다.

## 6.6.1. 동기

[키워드](../001-lexical/105-keywords.md) 의 예약 키워드 목록은 언어가 직접 정의하는 고정된 집합이다. 이 외의 키워드를
추가하려면 언어 사양을 수정해야 할까?

표준 라이브러리는 종종 키워드처럼 보이는 토큰을 도입하고 싶을 때가 있다. 예를 들어 어떤 라이브러리
DSL 의 도메인 키워드 같은 것이다. `#[keyword]` 매직이 라이브러리가 언어 수준 키워드를 등록하는 허가된 통로다.

## 6.6.2. 형태

```
keyword_attr    ::= "#" "[" "keyword" "(" string_lit ")" "]"
```

```nok
#[keyword("yield_priority")]
fn yield_priority_handler(...) { ... }

#[keyword("with")]
fn with_handler(...) { ... }
```

- `#[keyword("name")]` 형태이다. 인자로 키워드 이름 (문자열 리터럴) 을 받는다.
- 함수 또는 트레잇 메서드에 부착하면 그 항목이 키워드 처리기가 된다.

## 6.6.3. 등록의 효과

`#[keyword("name")]` 가 어딘가에 등록되면 다음 효과가 발생한다.

1. 그 컴파일 단위에서 식별자 `name` 이 키워드로 토큰화된다.
2. 파서가 그 키워드의 등장 위치에서 등록된 핸들러를 호출하는 desugar 를 적용한다.

이전에는 `name` 을 일반 식별자로 쓸 수 있었지만, 등록 후에는 키워드 토큰이 된다. 사용자 코드가
`name` 을 변수나 함수 이름으로 쓰면 컴파일 에러다.

## 6.6.4. 충돌 검사

```nok
#[keyword("if")]                  // ERROR — 'if' 는 예약 키워드
fn ... { ... }
```

[키워드](../001-lexical/105-keywords.md) 의 예약 키워드 목록과 충돌하면 등록 시점에 즉시 거부된다. 예약 키워드는 덮어쓸 수 없다.

서로 다른 라이브러리가 같은 키워드를 등록하려 하면 마찬가지로 충돌한다.

```
package_a 가 #[keyword("with")] 등록
package_b 도 #[keyword("with")] 등록    → 두 패키지를 한 빌드에 쓰면 ERROR
```

## 6.6.5. 적용 범위

`#[keyword]` 의 효력은 그 등록을 포함하는 컴파일 단위 (보통 패키지) 안에서만 유효하다. 다른 패키지에서는
같은 이름이 일반 식별자로 작동한다.

이 지역적 효과는 라이브러리 사이의 충돌을 줄이고, 어떤 패키지가 어떤 키워드를 도입하는지 사용자가 의식적으로 결정할 수 있게 한다.

## 6.6.6. 사용 패턴

`#[keyword]` 는 드물게 쓰이며, 주로 다음 경우에 도입된다.

- 도메인 특화 언어 (DSL). 표 데이터, 그리드, 회로 등 도메인 단어가 기존 식별자 자리에서 키워드처럼 동작하는 것이 자연스러울 때.
- 연산자 매직으로 표현하기 어려운 블록 또는 본체 형태의 새 구문.

대부분의 경우 함수와 트레일링 클로저의 조합으로 키워드처럼 보이는 패턴을 만들 수 있다 ([트레일링
클로저](../004-functions/408-trailing-closure.md)). 이 형태가 가능하면 그쪽을 우선한다.

## 6.6.7. scanner pre-pass 와의 결합

`#[keyword]` 의 등록을 언제 인식하는가는 컴파일러의 scanner pre-pass 가 처리한다.

1. 컴파일러는 parse 전에 source 파일들을 빠르게 스캔하여 `#[keyword(...)]` 등록을 모은다.
2. 등록 표를 lexer 에 전달한다.
3. 정식 어휘 분석에서 등록된 이름들이 키워드 토큰으로 분리된다.
4. 파서가 등록된 핸들러로 desugar 한다.

이 pre-pass 덕분에 등록의 위치 (몇 번째 파일, 몇 번째 줄) 와 무관하게 컴파일 단위 안에서
일관성이 유지된다. 사용자는 등록 순서를 의식할 필요가 없다.

## 6.6.8. 키워드 핸들러의 시그니처

핸들러 함수의 시그니처는 키워드의 사용 형태에 따라 결정된다. 표준 라이브러리의 키워드 슬롯들이 정의된 시그니처를 요구한다.

(정확한 시그니처 형태는 표준 라이브러리와 컴파일러 사양에서 정의한다.)

## 6.6.9. 컨텍스트 키워드의 부재 (재확인)

[키워드](../001-lexical/105-keywords.md) 에서 정한 컨텍스트 키워드 미도입 원칙은 등록된 키워드에도 적용된다.

`#[keyword("with")]` 가 등록되면 `with` 는 어디서든 키워드로 토큰화된다. "특정 위치에서만
키워드" 같은 형태는 도입하지 않는다.

이 일관성은 lexer 와 parser 의 단순함을 유지한다.

## 6.6.10. 등록의 가시성

`#[keyword]` 가 부착된 항목 자체의 가시성 ([가시성](../005-modules/506-visibility.md)) 은 항목 접근에만 적용된다. 키워드
등록 효과와는 별개다.

```nok
pub(pkg) fn keyword_handler(...) { ... }

#[keyword("with")]
fn another_handler(...) { ... }     // 키워드 등록 — 패키지 전체에 적용
```

핸들러를 외부에서 호출할 수 있는지는 가시성으로 결정된다. 키워드 등록 자체는 컴파일 단위 전체에 영향을 미친다.

## 6.6.11. `#[keyword]` 와 사용자 정의 매크로의 차이

다른 언어들의 매크로 시스템과 비교하면 다음과 같다.

- Rust proc macro: 임의 토큰 변환. 사용자가 자유롭게 코드를 생성한다. 위생은 별도.
- Lisp macro: 동적 매크로. 런타임에도 등록할 수 있다.
- nok `#[keyword]`: 컴파일 타임 키워드 등록. 핸들러 함수가 desugar 를 결정한다. 자유로운 토큰 변환은 불가.

nok 은 의도적으로 제한된 매크로 시스템을 갖는다. 표현력과 도구 친화성의 트레이드오프에서 도구 친화성을 우선한다.

## 6.6.12. 등록된 키워드 vs 함수 호출

```nok
// 키워드 형태
with(mutex) { critical(); }

// 함수 호출 형태 (등록 없이)
with_lock(mutex) { critical(); }     // 함수 + 트레일링 클로저
```

대부분의 DSL-like 패턴은 함수와 트레일링 클로저의 조합으로 충분하다. `#[keyword]` 등록은 그 형태로
표현이 부자연스러운 경우에 한정한다.

## 6.6.13. 평가 시점

키워드 등록은 scanner pre-pass 시점에 처리된다. 다른 메타 처리 (cfg, 메타 블록 확장 등) 보다 먼저다.

이 순서 덕분에 키워드 처리기 자체에 cfg 를 조건적으로 적용할 수도 있고, 메타 블록의 본체 안에서
키워드를 사용할 수도 있다.

## 6.6.14. 사용 자제 권장

`#[keyword]` 는 드물게, 신중히 사용한다. 등록할 때마다 언어 표면이 늘어나며, 다른 사용자가 새 키워드를 보고 의미를 추측해야 하는 부담이 생긴다.

가장 보편적으로 도입되는 언어 키워드는 [키워드](../001-lexical/105-keywords.md) 의 예약 목록에 직접 추가하는 편이 더
적절할 수 있다 (언어 사양 변경).
