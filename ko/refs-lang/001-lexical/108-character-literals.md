# 1.8. 문자 리터럴

문자 리터럴은 코드포인트 하나나 바이트 하나를 나타내는 토큰입니다.

## 1.8.1. 두 종류

```
char_lit    ::= "'" char_item "'"
              | "c'" byte_item "'"
char_item   ::= <any unicode codepoint except "'" or "\\"> | escape_seq
byte_item   ::= <any ASCII byte except "'" or "\\"> | byte_escape
byte_escape ::= "\\x" hex_digit hex_digit | escape_seq
```

### 일반 문자: `'A'`

```rok
'A'
'세'
'\n'
'\u{1F600}'
```

작은따옴표(`'`) 한 쌍 안에는 정확히 하나의 코드포인트를 두어야 합니다. 이스케이프 시퀀스는 [문자열 리터럴](107-string-literals.md)의 표를 그대로 따르며, `\\`, `\'`, `\"`, `\n`, `\r`, `\t`, `\0`, `\x`, `\u{...}` 등을 쓸 수 있습니다. `'\x41'`처럼 1바이트 형태로 적어도 되고, 결과는 ASCII 범위의 코드포인트 하나입니다. `'AB'`처럼 두 글자 이상을 담거나 빈 `''`을 쓰면 어휘 단계에서 에러입니다.

이 형태의 리터럴은 `char`(유니코드 스칼라값, 컴파일러 primitive)입니다. 메서드는 [stdlib 2.15](../../refs-standard-libraries/200-core/215-string.md)가 정의합니다.

### C 호환 문자: `c'A'`

```rok
c'A'
c'\n'
c'\x7F'
```

`c` 접두와 작은따옴표 한 쌍으로 이루어지며, 이스케이프 시퀀스는 [문자열 리터럴](107-string-literals.md)의 표를 그대로 따릅니다. 값은 반드시 `U+0000`-`U+00FF` 범위 안이어야 하고, 범위를 넘으면 어휘 에러입니다. 예를 들어 `c'세'`는 에러입니다. `'세'`는 `U+C138`이어서 한 바이트에 담을 수 없기 때문입니다. 소스가 UTF-8이므로 직접 적을 수 있는 글자는 ASCII뿐이며, 비 ASCII 1바이트 값(`U+0080`-`U+00FF`)은 `\xHH` 또는 `\u{H...}` 이스케이프로 적어야 합니다.

이 형태는 외부 함수 인터페이스([FFI](../000-meta/007-glossary.md#ffi-foreign-function-interface))의 8비트 문자 형인 기본 타입 `c_char`로 평가됩니다.

## 1.8.2. 두 종류를 분리한 이유

같은 토큰 형태(`'X'`)에 두 의미를 붙이지 않고, 접두로 명시적으로 나눕니다. 유니코드 의미의 문자와 C [ABI](../000-meta/007-glossary.md#abi-application-binary-interface)의 1바이트는 의미론이 다릅니다. 같은 표기로 묶으면 호환 함수를 호출할 때 의도를 밝힐 방법이 없어집니다. `c` 접두는 "FFI와 닿는 코드"라는 표시를 눈에 보이게 남기기도 합니다.

## 1.8.3. 길이 강제 검증

문자 리터럴은 정확히 하나의 코드포인트(일반) 또는 정확히 하나의 바이트(C 호환)를 담아야 합니다. 이 길이 검사는 어휘 단계에서 하며, 길이가 맞지 않으면 바로 에러입니다.

이렇게 정하면 다음과 같은 모호함이 없어집니다. 결합 문자(`e\u{0301}` = `é`)를 문자 리터럴 하나에 담을 수 있을까요? 코드포인트가 둘이므로 안 됩니다. 이런 글자는 문자열 리터럴에 두어야 합니다. 그래핌 클러스터 단위로 "눈에 한 글자"로 보이는 것도 문자 리터럴이 아니라 문자열 쪽 개념으로 다룹니다.

이렇게 단순화해서 "문자 = 코드포인트 한 개"라는 정의가 어휘 단계부터 일관되게 유지됩니다.
