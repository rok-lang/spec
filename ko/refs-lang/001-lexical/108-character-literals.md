# 1.8. 문자 리터럴

문자 리터럴은 단일 코드포인트 또는 단일 바이트를 표현하는 토큰이다.

## 1.8.1. 두 종류

```
char_lit    ::= "'" char_item "'"
              | "c'" byte_item "'"
char_item   ::= <any unicode codepoint except "'" or "\\"> | escape_seq
byte_item   ::= <any ASCII byte except "'" or "\\"> | byte_escape
byte_escape ::= "\\x" hex_digit hex_digit | escape_seq
```

### 일반 문자: `'A'`

```nok
'A'
'세'
'\n'
'\u{1F600}'
```

- 작은따옴표 (`'`) 한 쌍 안에 정확히 하나의 코드포인트를 둔다.
- 이스케이프 시퀀스는 [문자열 리터럴](107-string-literals.md) 의 표를 그대로 따른다 (`\\`, `\'`, `\"`,
  `\n`, `\r`, `\t`, `\0`, `\x`, `\u{...}`).
- `'\x41'` 같은 1바이트 형태도 정상이다. 결과는 ASCII 범위의 코드포인트 하나다.
- `'AB'` 처럼 두 글자 이상은 어휘 에러.
- 빈 `''` 도 어휘 에러.

평가될 라이브러리 타입의 정확한 이름은 타입 시스템 사양에서 정의한다. 본 문서는 어휘
형식만 다룬다.

### C 호환 문자: `c'A'`

```nok
c'A'
c'\n'
c'\x7F'
```

- `c` 접두와 작은따옴표 한 쌍.
- 이스케이프 시퀀스는 [문자열 리터럴](107-string-literals.md) 의 표를 그대로 따른다.
- 내용의 값은 `U+0000`-`U+00FF` 범위에 들어가야 한다. 이 범위를 넘으면 어휘 에러.
- `c'세'` 는 에러다. `'세'` 는 `U+C138` 이라 한 바이트에 담기지 않는다.
- 본문에 직접 표기해서 1바이트 범위를 채우려면 ASCII 글자만 가능하다 (소스가 UTF-8 이므로).
  비-ASCII 1바이트 값 (`U+0080`-`U+00FF`) 은 `\xHH` 또는 `\u{H...}` 이스케이프로 표기한다.

이 형태는 외부 함수 인터페이스 ([FFI](../000-meta/007-glossary.md#ffi-foreign-function-interface)) 의 8비트 문자 형과 호환되는 라이브러리 타입으로
평가된다. 정확한 타입 이름은 타입 시스템 사양에서 정의한다.

## 1.8.2. 두 종류를 분리한 이유

같은 토큰 형태 (`'X'`) 에 두 가지 의미를 매기지 않고 접두로 명시 분리한다.

- 유니코드 의미의 문자와 C [ABI](../000-meta/007-glossary.md#abi-application-binary-interface) 의 1바이트는 의미론이 다르다. 같은 표기로 묶으면 호환
  함수를 호출할 때 의도를 명시할 방법이 없다.
- `c` 접두 자체가 "FFI 와 닿는다" 는 신호를 시각적으로 남긴다.

## 1.8.3. 길이 강제 검증

문자 리터럴은 정확히 하나의 코드포인트(일반) 또는 정확히 하나의 바이트(C 호환) 를 담아야
한다. 이 길이 검증은 어휘 단계에서 수행하며, 길이가 맞지 않으면 즉시 에러를 낸다.

이 결정은 다음과 같은 모호함을 차단한다.

- 결합 문자 (`e\u{0301}` = `é`) 를 한 문자 리터럴에 담을 수 있는가? 코드포인트가 둘이므로
  허용하지 않는다. 이런 글자는 문자열 리터럴에 두어야 한다.
- 그래픽 클러스터 단위의 "사람 눈에 한 글자" 는 문자 리터럴이 아니라 문자열 영역의 개념이다.

이 단순화 덕분에 _문자 = 코드포인트 한 개_ 라는 정의가 어휘 단계부터 일관되게 유지된다.
