# 2.7. niche 최적화

niche 는 어떤 타입의 유효 비트 패턴 중 절대 등장하지 않는 비트 패턴이다. 합 타입의 태그를 이런 비트 패턴에 겹쳐 저장하면 태그 자리를 따로 두지 않아도 된다. 메모리 오버헤드 0 인 합 타입이 만들어진다.

이 최적화는 [합 타입](206-sum-types.md) 의 메모리 표현이 컴파일러 자유라는 사실 위에서 작동한다.

## 2.7.1. 동기

```nok
let p: Ptr<u8> | none      // 64-bit 포인터 + none
```

위가 16 바이트 (포인터 8 + 태그 1 + 패딩 7) 가 아니라 8 바이트로 표현될 수 있어야 한다. 포인터의 `null` 비트 패턴 (0x0000_0000_0000_0000) 이 유효한 포인터에서 등장하지 않으므로 그 자리를 `none` 의 자리로 쓸 수 있다.

이 절약은 과학·데이터 코드의 핵심 메모리 효율로 이어진다 (Julia 의 isbits `union` 에서 영감).

## 2.7.2. 자동 niche

다음 타입에서는 컴파일러가 자동으로 niche 를 식별한다. 사용자가 따로 표시할 필요가 없다.

| 타입                     | niche 비트 패턴                                       |
| ------------------------ | ----------------------------------------------------- |
| `Ptr<T>` / `ConstPtr<T>` | null 포인터 (`0x0`)                                   |
| `bool`                   | 2 ~ 255 (`0` / `1` 만 유효)                           |
| `char`                   | 서로게이트 범위 (`U+D800` ~ `U+DFFF`) 와 `> U+10FFFF` |
| `enum`                   | 미사용 discriminant 값                                |

위 타입을 합 타입의 한 항으로 쓰고 다른 항이 unit-like (예: `none`) 이면, 합 타입의 크기가 그 항의 크기와 같아진다.

```nok
Ptr<u8> | none           // 8 바이트 (자동 niche)
bool | none              // 1 바이트 (자동 niche)
```

## 2.7.3. 자동 없음

다음 타입은 모든 비트 패턴이 유효하므로 자동 niche 가 없다.

- 정수형 — `i8`, `i16`, `i32`, `i64`, `u8`, `u16`, `u32`, `u64`, `usize`, `isize`
- 부동소수형 — `f32`, `f64`

이들에 niche 가 필요하면 opt-in 메커니즘을 쓴다.

## 2.7.4. opt-in niche. `#[niche(...)]` 속성

```
niche_attr      ::= "#" "[" "niche" "(" niche_arg ("," niche_arg)* ","? ")" "]"
niche_arg       ::= const_expr | range_expr
```

어떤 비트 패턴이 niche 인지 사용자가 명시할 수 있다.

```nok
#[niche(0)]
struct NonZero<T>(T);

#[niche(0, -1, I32_MIN)]
struct Restricted(i32);

#[niche(I32_MIN..=-1)]
struct PositiveOrZero(i32);

#[niche(f64::POS_INF, f64::NEG_INF)]
struct FiniteF64(f64);
```

규칙:

- `#[niche(...)]` 속성은 newtype `struct` (단일 필드 tuple `struct`) 에만 직접 부착한다.
- 인자는 `const` 표현식 또는 범위 표현식 (`..=`, `..`).
- 다중 인자는 콤마로 구분한다. 합집합으로서의 niche 비트 패턴.
- 사용자가 명시한 비트 패턴은 유효한 값이 아니라는 약속이다. 컴파일러가 검증하지 않는다. 사용자가 그 약속을 어기면 합 타입의 태그가 손상된다 (의미 정의되지 않음).

> [!WARNING]
> opt-in niche 는 사용자의 약속이다. 컴파일러는 약속 위반을 검출하지 않는다. niche 자리에 해당하는 비트 패턴이 등장하면 합 타입의 태그가 잘못 해석된다.

여러 필드를 가진 구조체에 niche 필드가 포함되면 자동으로 전파된다. 가장 큰 niche 를 가진 필드가 구조체 전체의 niche 가 된다.

```nok
struct PointWithMaybeColor {
    x: f64;
    y: f64;
    color: NonZero<u32>;     // niche 가 있는 필드
}
// PointWithMaybeColor | none 도 추가 비용 0 (color 의 niche 사용)
```

## 2.7.5. 부착 가능한 위치

`#[niche(...)]` 속성은 다음에서만 의미를 갖는다.

- newtype tuple `struct` (단일 필드).
- 자동 niche 가 있는 `enum`, 또는 기존 niche 가 있는 `struct` 를 한 필드로 갖는 newtype.

다음에는 직접 부착할 수 없다.

- 원시 타입 (`i32` 등). 사용자 정의 타입이 아니다.
- `enum`. 자동 niche 메커니즘이 우선한다.
- `union`. 비트 재해석 의미상 niche 정의가 의미 없다.

## 2.7.6. 표준 라이브러리 wrapper

자주 쓰는 niche 패턴용 wrapper 가 표준 라이브러리에 미리 정의되어 있다.

| 이름          | 의미                                 |
| ------------- | ------------------------------------ |
| `NonZero<T>`  | 정수형 T 에 대해 0 이 niche          |
| `NonNan<F>`   | 부동소수 F 에 대해 NaN 이 niche      |
| `Finite<F>`   | 부동소수 F 에 대해 NaN + ±∞ 가 niche |
| `Positive<T>` | T 의 음수 영역이 niche               |

이들의 정확한 정의는 표준 라이브러리 사양에서 한다. 본 문서는 언어가 niche 메커니즘을 제공한다는 사실까지만 정의한다.

## 2.7.7. 합 타입과의 결합

합 타입 (`A | B`) 의 메모리 크기는 다음 규칙으로 결정된다.

1. 모든 항의 비트 표현이 서로 겹치지 않는 niche 자리를 통해 구분 가능한가?
2. 가능하면 가장 큰 항의 크기 + niche 자리 (별도 태그 없음).
3. 불가능하면 가장 큰 항의 크기 + 별도 태그 (1 ~ N 비트).

이 규칙의 정확한 알고리듬은 컴파일러 구현이 결정한다. 사양은 결과 (위 두 경우의 크기) 만 보장한다.

## 2.7.8. 사용자가 알아야 하는 것

niche 최적화는 대부분 자동이다. 사용자가 명시적으로 하는 일은 두 가지다.

- 기존 타입의 제약된 부분 집합을 만들고 싶을 때 newtype + `#[niche(...)]`.
- 표준 라이브러리의 wrapper 를 그대로 쓸 때.

opt-in niche 의 불변을 유지하는 책임은 사용자에게 있다.
