# 2.12. 트레잇-as-타입 금지

> [!IMPORTANT]
> 트레잇 이름을 타입 표현식 자리에 그대로 적는 것은 금지입니다. 런타임에 구현 타입이 정해지는 값이 필요하면, 비용이 문법에 드러나는 `any Trait`을 적습니다(2.12.3).

## 2.12.1. 금지 항목

```rok
let a: Number = 32i32;                          // ERROR: Number 는 트레잇
fn process(x: Display) -> str { ... }            // ERROR
struct Holder { item: Iterator; }                // ERROR
```

위 예처럼 변수 타입, 매개변수 타입, 반환 타입, 구조체 필드 타입 어디든 트레잇 이름이 그대로 나오면 컴파일 에러입니다.

## 2.12.2. 금지의 근거

금지 대상은 **숨은** 동적 디스패치입니다. 트레잇 이름을 타입 자리에 그대로 적으면 겉보기에는 평범한 정적 타입과 구별되지 않지만, 실제로는 런타임 디스패치가 생깁니다. 이 디스패치는 비용이 작지 않습니다. 실행 시점에 구현을 골라 호출하므로, 분기 예측이 빗나가면 직접 호출보다 두 배 넘게 느려질 수 있습니다. 디스패치 자료를 읽느라 메모리 접근이 늘어 캐시 효율도 떨어집니다. 무엇보다 컴파일러의 인라이닝과 최적화를 막습니다.

과학 코드와 데이터 코드의 중심 수치 루프가 모르는 사이에 이 비용을 떠안지 않도록, Rok은 맨 트레잇 이름을 타입으로 쓰지 못하게 합니다. 런타임 다형성은 `any`라고 적은 자리에만 있습니다. `any Trait`은 동적 디스패치 비용이 `any` 키워드로 문법에 드러나므로 허용합니다.

## 2.12.3. 다형성이 필요할 때. 세 대안

다형성이 필요할 때 쓸 수 있는 대안은 세 가지입니다.

### 1. 닫힌 후보가 있으면 합 타입

후보 집합이 미리 정해져 있으면 합 타입을 씁니다.

```rok
let a: i32 | f32 | f64 = 32i32;
fn process(x: i32 | f32) -> str { ... }
```

후보가 컴파일 타임에 정해져 있을 때 알맞습니다. 메모리와 디스패치 비용이 분명히 드러나고([합 타입](206-sum-types.md) 참고), 패턴 매칭의 완전성도 검사할 수 있습니다.

### 2. 열린 다형성이면 제네릭

후보가 열려 있으면 제네릭을 씁니다.

```rok
fn process<T: Display>(x: T) -> str { ... }
struct Holder<T: Iterator> { item: T; }
```

후보가 컴파일 타임에 정해지지 않거나 호출자마다 다를 때 알맞습니다. 단형화로 직접 호출되므로 비용은 0에 가깝고([제네릭](210-generics.md) 참고), 트레잇 바운드로 메서드도 호출할 수 있습니다.

### 3. 런타임에 구현 타입이 정해지면 `any Trait`

한 슬롯이나 컬렉션에 구현 타입이 서로 다른 값을 섞어 담아야 하면 제약 붙은 `any`를 씁니다.

```rok
let shapes: List<any Shape> = [Circle { r: 1.0 }, Square { side: 2.0 }];
fn report(e: any Error) -> str { f"{e}" }
struct ConfigError { msg: str; cause: any Error | none; }
```

`any Trait` 슬롯에는 `Trait`을 구현하는 타입의 값만 넣을 수 있으며(컴파일 타임 검사), 그 값에서는 `Trait`과 그 슈퍼트레잇의 메서드를 호출할 수 있습니다. 호출은 런타임 태그로 디스패치되며, 비용 모델은 [`any` 슬롯](202-any-slot.md)과 같습니다. 정확한 규칙은 [2.2.10](202-any-slot.md#2210-제약-붙은-any-any-trait)에서 정의합니다.

## 2.12.4. 결정 기준

대안은 다음 기준으로 고릅니다.

| 상황                                               | 선택        |
|----------------------------------------------------|-------------|
| 후보가 고정된 작은 집합 (3~5 개)                   | 합 타입     |
| 후보가 유저 / 라이브러리 확장 가능                 | 제네릭      |
| 후보가 런타임에만 결정 (예: 플러그인, 이종 컬렉션) | `any Trait` |
| 어떤 제약도 없이 무엇이든 담아야 함                | `any`       |

세 번째 경우처럼 런타임에 타입이 정해지는 다형성이 필요하면 `any Trait`을 씁니다. 동적 디스패치 비용이 들지만, 그 비용은 `any`라고 적은 자리에만 드러나게 모입니다.

## 2.12.5. 슈퍼트레잇과 바운드 표현은 허용

분명히 해 두면, 금지하는 것은 타입 위치에 나오는 트레잇 이름뿐입니다. 다음은 모두 허용합니다.

```rok
trait Ord: Eq { ... }                            // 슈퍼트레잇 선언
fn f<T: Add + Display>(x: T) { ... }              // 트레잇 바운드
fn g<T>(x: T) where T: Ord, T: Clone { ... }      // where 절
impl Display for Point { ... }                    // impl 의 트레잇 자리
```

이 위치에서 트레잇 이름은 타입이 아니라 제약을 나타냅니다.

## 2.12.6. 컴파일 에러의 형태

트레잇 이름이 타입 위치에 나오면 컴파일러는 다음과 비슷한 진단을 출력합니다.

```
ERROR: 'Display' is a trait, not a type.
       To allow multiple types, use generics, a sum type, or `any Display`:
         fn f<T: Display>(x: T) { ... }
         fn f(x: SomeType | OtherType) { ... }
         fn f(x: any Display) { ... }
```

이 진단은 사용자를 앞에서 소개한 세 대안 중 하나로 안내합니다.
