# 2.5. `union`

`union`은 여러 필드가 같은 메모리를 공유하는 비태그 컨테이너입니다. 어느 시점에 어느 필드의 값이 의미 있는지 언어는 추적하지 않습니다. 그 책임은 코드를 쓰는 사람에게 있습니다.

```
union_decl      ::= "union" identifier generics? where_clause? "{" named_field_list? "}"
```

## 2.5.1. 기본 형태

가장 단순한 `union`은 다음과 같이 선언합니다.

```rok
union EpollData {
    ptr: usize;
    fd: i32;
    val: u64;
}
```

본체와 필드 문법은 [`struct`](203-struct.md)의 named `struct`와 같습니다. 다른 점은 두 가지입니다. 키워드가 `union`이고, 모든 필드가 같은 메모리 위치를 공유합니다.

### 제네릭 union

`union`에도 `struct`처럼 타입 매개변수([2.10](210-generics.md))를 둘 수 있고, 바운드와 `where` 절, 기본값도 쓸 수 있습니다. 각 인스턴스는 레이아웃이 따로 있는 별개의 타입입니다. 크기와 정렬은 그 인자로 정해진 필드 타입을 따릅니다.

```rok
union Bits<T> { v: T; raw: u64; }
union Small<T = u16> { v: T; raw: u8; }

let a = Bits::<f64> { raw: 0x3FF0000000000000u64 };
let b = Bits { v: 7i32 };              // 준 필드에서 추론한 Bits<i32>
let x = unsafe { a.v };                // 1.0 (the bits of 1.0f64)
```

union 리터럴의 타입 인자는 주어진 필드 하나에서 추론합니다. 컴파일러는 바운드를 인스턴스마다 검사하고, 진단에는 인스턴스 이름을 그대로 씁니다(``reading field `v` of union `Bits<i32>` needs an `unsafe` block``). `union`은 필드를 적어도 하나 선언합니다.

## 2.5.2. 의미론

다음 예는 `union`의 동작을 보여 줍니다.

```rok
let x = EpollData { fd: 5i32 };
x.fd = 7i32;                    // 쓰기: 안전
let y = unsafe { x.val };       // 읽기: unsafe 필요. x 의 비트 패턴을 u64 로 재해석
```

어떤 필드로 인스턴스를 만들면 그 필드의 비트가 메모리에 쓰입니다. 나중에 다른 필드로 읽으면 같은 메모리의 비트를 그 필드 타입으로 재해석합니다. 필드 쓰기는 안전하지만, 필드 읽기는 [`unsafe`](../004-functions/415-unsafe.md#4152-unsafe----블록-표현식) 안에서만 할 수 있습니다. 읽은 비트가 그 타입(예: `bool`, `char`, 포인터)의 유효한 값인지 언어가 보장하지 않기 때문입니다.

## 2.5.3. 안전성의 위치

`union`의 비트 재해석은 언어가 정의한 동작입니다. 하지만 결과가 무슨 의미인지는 프로그램 도메인이 책임집니다. 예를 들어 `f32` 필드에 `1.0`을 쓰고 `i32` 필드로 읽으면 `1065353216`(`0x3F800000`)이 됩니다. 반대로 `i32` 비트를 `f32`로 읽으면 IEEE 754 비트 표현에 따른 실수 값이 됩니다. 그 값이 도메인에서 의미가 있는지는 언어가 검사하지 않습니다.

이 모델은 C의 `union`과 다릅니다. C에서는 다른 멤버로 읽는 것(read-from-different-member)이 미정의 동작입니다. Rok은 이를 비트 재해석으로 정의합니다. 다만 결과가 유효한 값이라는 보장이 없으므로 읽기는 `unsafe`로 표시합니다.

## 2.5.4. 기본 레이아웃은 컴파일러 자유

기본 `union` 레이아웃은 컴파일러에 맡깁니다. 가장 큰 필드의 크기와 정렬만 만족하면 됩니다. 필드 정렬과 패딩은 컴파일러가 정합니다.

C [ABI](../000-meta/007-glossary.md#abi-application-binary-interface)와 호환되는 `union`이 필요하면 `#[repr(C)]`를 붙입니다.

```rok
#[repr(C)]
union CUnion {
    a: i32;
    b: f32;
}
```

`#[repr(C)]`를 붙인 `union`은 C의 `union`과 비트 수준에서 호환되고, [FFI](../000-meta/007-glossary.md#ffi-foreign-function-interface) 인터페이스에서 씁니다. 정확한 의미는 [내장 속성](../006-meta-system/602-built-in-attributes.md)에서 정의합니다.

## 2.5.5. `union`과 `#[repr(C)] union`의 차이

두 형태의 차이는 다음과 같습니다.

| 형태                         | 사용처    | 레이아웃      | 비트 호환           |
|------------------------------|-----------|---------------|---------------------|
| `union T { ... }`            | 일반 코드 | 컴파일러 자유 | Rok 내부에서만 보장 |
| `#[repr(C)] union T { ... }` | FFI       | C ABI 동일    | C 코드와 호환       |

## 2.5.6. 가시성 / 중복 정의

[`struct`](203-struct.md)와 같은 규칙을 따릅니다.

> [!WARNING]
> `union` 필드 읽기는 비트 재해석이고, `unsafe` 안에서만 할 수 있습니다. 쓰기는 안전합니다. 읽은 비트가 그 타입의 유효한 값인지, 도메인에서 의미가 있는지는 작성자가 책임집니다.

## 2.5.7. `union`과 합 타입의 차이

`union`과 합 타입은 겉보기에 비슷하지만 전혀 다른 도구입니다.

```rok
union  Foo { a: i32; b: f32; }    // 같은 메모리, 태그 없음
type   Bar = i32 | f32;            // 별개 메모리, 태그 있음
```

측면별 차이는 다음과 같습니다.

| 측면                      | `union`                        | 합 타입 (`A \| B`)            |
|---------------------------|--------------------------------|------------------------------|
| 어느 필드가 활성인지 추적 | 하지 않습니다                  | 태그로 추적                  |
| 필드 사이 변환            | 비트 재해석                    | 변형 변경 (값 재구성)        |
| 메모리 사용               | 가장 큰 필드 크기              | 태그 + 가장 큰 변형 크기     |
| 필드 읽기                 | `unsafe` 필요 (비트 재해석)    | 패턴 / `is`로 안전하게       |

두 도구는 용도가 완전히 다릅니다. `union`은 같은 비트를 다르게 해석하는 도구입니다. 합 타입은 값 수준에서 서로 다른 종류를 표현하는 도구입니다. 둘을 혼동하면 안 됩니다.
