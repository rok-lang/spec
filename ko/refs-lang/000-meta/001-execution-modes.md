# 0.1. 실행 엔진과 사용자 표면

nok 의 실행 모델은 두 축으로 구성된다. **실행 엔진** 은 코드가 기계어가 되는 방식이고, **사용자 표면** 은 사용자가 코드를 입력하고 결과를 받는 환경이다. 엔진은 둘, 표면은 셋. 같은 엔진을 여러 표면이 공유하므로 엔진의 가짓수가 표면보다 적다.

## 0.1.1. 실행 엔진

### JIT (Just-in-Time)

코드 조각이 입력되는 즉시 컴파일하여 실행한다.

- 한 입력 단위 (줄, 셀) 는 그 직전까지 누적된 상태 — 변수, 함수, 가져온 모듈 — 를 본다.
- 새 입력이 기존 정의를 덮어쓰면 이후 입력은 새 정의를 본다.
- 컴파일 결과는 메모리와 디스크에 캐시된다. 같은 입력의 재실행은 즉시 끝난다.

### AOT (Ahead-of-Time)

소스 전체를 미리 컴파일하여 단일 산출물 (실행 파일 또는 정적 라이브러리 `.a`) 로 만든다.

- 실행 시작 시 컴파일 비용은 없다.
- 다른 nok 코드에서 라이브러리로 링크할 수 있다.
- 런타임에 새 코드를 추가할 수 없다.

### 의미론은 같다

> [!IMPORTANT]
> 두 엔진은 같은 의미론을 공유한다. JIT 에서 동작한 코드는 AOT 빌드에서도 같은 결과를 낸다. 차이는 _컴파일 시점_ 에만 있다. 본 사양은 두 엔진에 동시에 적용되며, 한쪽에만 적용되는 의미론은 없다.

JIT 와 AOT 는 [용어집](007-glossary.md) 의 약어 그대로 사용한다.

### 같은 파이프라인을 공유한다

JIT 도 AOT 도 동일한 컴파일 파이프라인을 거친다. 소스에서 시작해 표준 중간 표현 ([0.2. 컴파일 파이프라인](002-pipeline.md)) 의 텍스트가 나올 때까지 두 엔진은 같은 코드를 실행한다. 분기는 그 마지막 중간 표현 이후에만 일어난다.

- **JIT 엔진** 은 중간 표현을 in-process 실행 엔진에 넘겨 즉시 기계어로 옮기고 호출한다.
- **AOT 엔진** 은 중간 표현을 표준 도구 체인에 넘겨 네이티브 바이너리로 빌드한다.

이 구조에서 한 컴파일러 구현이 두 엔진을 모두 담당한다. 동작 차이가 발생하면 그 원인은 컴파일러가 아니라 실행 시점 환경 (메모리, 스레드, OS 자원) 이다.

## 0.1.2. 사용자 표면

### REPL

터미널에서 한 줄 또는 한 식을 입력하면 즉시 평가되어 결과가 출력된다.

- 탐색, 수식 시연, 타입 확인 용도.
- 변수와 함수 정의가 입력 사이에 누적된다.
- 마지막 표현식의 값과 타입이 자동으로 표시된다.

엔진은 JIT. 입력 단위는 한 줄 또는 한 식.

### Jupyter

Jupyter / JupyterLab 의 nok 커널로 동작한다. 한 셀 단위로 평가하며, 결과는 노트북 안에 시각화, 테이블, 텍스트로 남는다.

- 데이터 분석의 표준 작업 흐름을 지원한다.
- 셀을 재실행하면 이전 정의가 교체된다.

엔진은 JIT. 입력 단위는 한 셀. Jupyter 표면은 두 가지 배포 형태로 제공된다.

#### 로컬 네이티브 커널

사용자 PC 의 Jupyter 프론트엔드 (JupyterLab, classic Notebook, VS Code 등) 가 별개 프로세스로 nok 커널 바이너리를 실행하고, ZeroMQ 기반 Jupyter 5.5 wire protocol 로 통신한다.

- 5 개의 ZMQ 소켓 채널 (shell, iopub, control, stdin, heartbeat) 위에 메시지를 주고받는다. 각 메시지는 HMAC 서명된다.
- nok 와 함께 배포되는 kernelspec JSON 이 커널 바이너리의 위치와 인자를 Jupyter 에 알린다.
- 커널 바이너리는 자신이 도는 OS 의 모든 기능 (파일 시스템, 네트워크, 표준 출력, 외부 프로세스) 을 그대로 사용할 수 있다.

이 형태는 IPython, IJulia, IHaskell, xeus-cling 등 네이티브 Jupyter 커널의 표준 모델이며, nok 도 같은 방식을 따른다.

#### 브라우저 WASM 커널

JupyterLite 구도. 모든 것이 브라우저 안에서 동작하며 OS 가 매개되지 않는다.

- nok 커널이 WebAssembly 로 빌드되어 페이지에 로드된다. 빌드 타깃 식별자는 [0.6. 플랫폼 타깃](006-platform-targets.md) 에서 정의한다.
- 통신은 브라우저 메시지 채널 (Web Worker, SharedArrayBuffer) 을 사용한다.
- OS 자원이 없으므로 파일 시스템, 네트워크, 외부 프로세스 관련 라이브러리는 빌드에 포함되지 않는다.

설치 없이 노트북을 데모, 교육, 임시 환경에서 실행하는 용도다. 사용자 비중은 로컬 커널보다 작지만, 본 사양은 두 형태를 모두 정식 지원 대상으로 본다.

### AOT 산출물

소스를 빌드한 실행 파일을 직접 실행하거나, 만든 정적 라이브러리를 다른 빌드에 링크한다.

엔진은 AOT.

## 0.1.3. 엔진과 표면의 매핑

```
                ┌── REPL (터미널)
   JIT 엔진 ────┤
                └── Jupyter ──┬── 로컬 네이티브 커널 (ZMQ)
                              └── 브라우저 WASM 커널

   AOT 엔진 ──── 산출물 직접 실행
```

세 표면이 두 엔진을 공유한다.

## 0.1.4. 구현 우선순위

본 사양과 초기 구현은 다음 순서를 따른다.

1. AOT 엔진. 가장 단순한 종착점이며 모든 의미론의 기준.
2. JIT 엔진. AOT 위에 얹는 증분 레이어.
3. 표면. REPL, 로컬 Jupyter 커널, 브라우저 Jupyter 커널 순.

사양이 모호한 지점에서는 AOT 의미가 우선한다. JIT 은 AOT 의 의미를 증분으로 재현하는 역할이다.
