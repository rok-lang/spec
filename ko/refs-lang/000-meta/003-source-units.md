# 0.3. 소스 단위

nok 의 컴파일 단위는 **패키지** 다. 패키지는 파일 시스템 위에서 정해진 규약으로 인식되며,
별도의 매니페스트 파일은 사용하지 않는다.

## 0.3.1. 패키지의 두 종류

### 실행 패키지: `main.nok`

루트 디렉토리에 `main.nok` 가 있으면 실행 패키지로 인식된다.

```
my_app/
├── main.nok          ← 진입점
├── ...               ← 부속 파일들
```

`main.nok` 의 최상위 함수 중 진입점에 해당하는 함수가 실행된다. 진입점의 정확한 형태는
함수 사양에서 정의한다.

### 라이브러리 패키지: `lib.nok`

루트 디렉토리에 `lib.nok` 가 있으면 라이브러리 패키지로 인식된다.

```
my_lib/
├── lib.nok           ← 라이브러리 루트
├── ...
```

라이브러리 패키지는 진입점이 없다. 외부에서 불러서 쓰는 정의 묶음이다.

`main.nok` 와 `lib.nok` 는 한 패키지에서 동시에 존재할 수 없다.

## 0.3.2. 파일과 모듈

패키지 안의 추가 소스 파일은 두 형태 중 하나를 택한다.

```
foo.nok                ← 단일 파일 모듈
```

또는

```
foo/
├── ...nok            ← 디렉토리 모듈 (여러 파일을 묶음)
```

같은 모듈 이름을 두 형태로 동시에 쓸 수 없다. `foo.nok` 와 `foo/` 가 함께 있으면 에러다.

## 0.3.3. 패키지 식별자

패키지에는 내용 기반 해시가 부여된다. 모든 소스 파일을 정해진 순서로 직렬화한 SHA-256 의
앞 8 글자를 식별자로 쓴다.

- 같은 내용의 패키지는 어디서 빌드해도 같은 해시.
- 한 글자라도 바뀌면 새 해시.

이 해시는 산출물의 심볼 이름과 캐시 키에 사용된다. 구체적 사용처는 후속 문서에서 정의한다.

## 0.3.4. 메타 파일을 두지 않는 이유

초기 nok 의 패키지 정의는 파일 존재만으로 결정된다. 의존성 명세, 빌드 설정, 버전 핀은
별도 도구가 다룰 영역이며 본 사양의 범위 밖이다.

이 결정은 두 가지를 가능하게 한다.

- 컴파일러가 단독으로 패키지를 처리할 수 있다. 외부 도구 의존이 없다.
- 패키지 매니저가 나중에 등장해도 기존 패키지 정의가 깨지지 않는다. 메타 파일은 추가될
  뿐이며 기존 규약을 바꾸지 않는다.
