# 0.3. 소스 단위

rok 의 컴파일 단위는 **패키지**입니다. 패키지는 파일 시스템 위에서 정해진 규약 (`main.rok` / `lib.rok`) 으로 인식됩니다. 매니페스트 `Rok.toml` 은 의존성 등을 선언할 때만 두며, 의존성이 없는 패키지에는 필요하지 않습니다 (0.3.4).

## 0.3.1. 패키지의 두 종류

패키지는 역할에 따라 실행 패키지와 라이브러리 패키지로 나뉩니다. 두 종류 모두 루트 디렉토리에 놓이는 특정 파일의 존재만으로 구분됩니다.

### 실행 패키지: `main.rok`

먼저 실행 패키지를 살펴보겠습니다. 루트 디렉토리에 `main.rok` 가 있으면 실행 패키지로 인식됩니다.

```
my_app/
├── main.rok          <- entry point
├── ...               <- other files
```

> entry point: 진입점. other files: 부속 파일들.

`main.rok` 는 진입 모듈로서, 명시적인 `fn main` 이나 top-level 문 가운데 한 가지 형태로 진입점을 제공합니다. 진입점의 정확한 형태와 top-level 문의 의미는 [4.16 진입점](../004-functions/416-entry-point.md) 에서 정의합니다. 패키지에 속하지 않은 단일 파일을 실행하면 그 파일이 익명 패키지의 `main.rok` 로 취급됩니다 ([4.16.8](../004-functions/416-entry-point.md#4168-단일-파일-실행)).

### 라이브러리 패키지: `lib.rok`

다음으로 라이브러리 패키지입니다. 루트 디렉토리에 `lib.rok` 가 있으면 라이브러리 패키지로 인식됩니다.

```
my_lib/
├── lib.rok           <- library root
├── ...
```

> library root: 라이브러리 루트.

라이브러리 패키지에는 진입점이 없으며, 외부에서 불러서 쓰는 정의 묶음의 역할을 합니다. `lib.rok` 를 포함한 `main.rok` 이외의 모든 모듈 파일은 항목만 담을 수 있고 top-level 문을 둘 수 없으므로, 모듈을 가져오는 일은 어떤 코드도 실행하지 않습니다 ([4.16.6](../004-functions/416-entry-point.md#4166-모듈은-정의-전용)). 또한 `main.rok` 와 `lib.rok` 는 한 패키지에서 동시에 존재할 수 없습니다.

## 0.3.2. 파일과 모듈

이제 패키지 내부의 모듈 구성을 살펴보겠습니다. 패키지 안의 추가 모듈은 두 형태 중 하나를 택합니다.

```
foo.rok                <- single-file module (no submodules)
```

또는 다음과 같이 폴더를 동반하는 형태로 둘 수도 있습니다.

```
foo.rok                <- module body
foo/                   <- foo's submodules
├── bar.rok                foo::bar submodule
└── baz.rok                foo::baz submodule
```

> single-file module: 단일 파일 모듈 (서브모듈 없음). module body: 모듈 본체. foo's submodules: foo 의 서브모듈들.

폴더 형태에서는 본체 파일 (`foo.rok`) 과 같은 이름의 폴더 (`foo/`) 가 함께 놓입니다. 이때 본체 안에 `mod 이름;` 으로 선언된 서브모듈만 폴더 안의 파일과 매핑됩니다. Rust 2018+ 와 같은 규칙이며, 자세한 매핑 규칙은 [모듈](../005-modules/504-modules.md) 에서 정의합니다.

한편 별도 파일 없이 본체 안에 `mod 이름 { ... }` 또는 `pub mod 이름 { ... }` 형태로 인라인 모듈을 둘 수도 있습니다. Rust 의 인라인 모듈과 같은 동작이며, 자세한 형태와 매핑 역시 [모듈](../005-modules/504-modules.md) 에서 정의합니다.

## 0.3.3. 패키지 식별자

각 패키지에는 내용 기반 해시가 부여됩니다. 해시 입력은 패키지의 모든 소스 파일을 패키지 기준 상대 경로 (`/` 구분자) 의 바이트 순서로 정렬해 이어 붙인 것이며, 각 파일은 `경로 + \0 + 내용 + \0` 으로 직렬화합니다. 그 SHA-256 의 앞 8 글자를 식별자로 사용합니다.

이 해시는 다음과 같은 성질을 가집니다. 같은 내용의 패키지는 어디서 빌드해도 같은 해시가 나오며, 한 글자라도 바뀌면 새 해시가 만들어집니다.

이 해시는 산출물의 심볼 이름과 캐시 키에 사용되며, 구체적 사용처는 후속 문서에서 정의합니다.

## 0.3.4. 매니페스트 (`Rok.toml`) 는 선택

> [!NOTE]
> 매니페스트와 lockfile 은 계획된 기능입니다 ([9.10](../009-tools/910-rok-frontend.md)).

패키지의 정의는 파일 존재만으로 결정됩니다. 패키지 루트에 `main.rok` 나 `lib.rok` 가 있으면 패키지이고, 어느 쪽이냐가 종류를 정합니다. 매니페스트는 이 규약을 바꾸지 않습니다.

의존성, dev 의존성, toolchain 고정 같은 정보가 필요할 때만 패키지 루트에 매니페스트 `Rok.toml` 을 두고, 도구가 해소한 결과는 lockfile `Rok.lock` 에 남습니다. 두 파일 이름은 이 철자 그대로 (첫 글자만 대문자) 입니다. 대소문자가 다른 이름 (`rok.toml`, `ROK.toml` 등) 은 경고입니다.

이 결정은 두 가지를 가능하게 합니다. 첫째로 의존성이 없는 패키지는 컴파일러가 파일만 보고 처리할 수 있습니다. 둘째로 매니페스트는 추가될 뿐이며, 기존 패키지 정의를 깨지 않습니다.
