# 0.5. 표준 라이브러리 계층

표준 라이브러리는 세 계층으로 나뉜다. 사용 가능한 환경과 노출하는 동작의 위험도를 기준으로
구분한다.

## 0.5.1. 세 계층

```
  unsafe   ←   안전 보장 없음. 원시 메모리·FFI·전송 가능 비트 캐스팅.
     ↑
   core    ←   모든 타깃에서 사용 가능한 안전 계층. 내부적으로는 unsafe 를 쓴다.
     ↑
    std    ←   타깃 종속 계층. 파일 시스템·네트워크·OS 스레드 등.
```

화살표는 의존 방향이다.

- `core` 는 `unsafe` 를 내부 구현에 사용할 수 있다.
- `std` 는 `core` 와 `unsafe` 를 모두 사용할 수 있다.
- 반대 방향 의존은 금지된다.

## 0.5.2. 각 계층의 책임

### `unsafe`

저수준이며 위험한 영역. 컴파일러가 안전성을 보증할 수 없는 동작이 모인다.

- 원시 포인터 형태 (raw pointer 추상)
- 임의 비트 캐스팅 (`transmute` 류)
- 핀(pinning), volatile 메모리 접근
- C [ABI](007-glossary.md#abi-application-binary-interface) 호환 메모리 할당의 원형

이 계층의 함수를 호출하는 쪽이 안전성을 책임진다. 이름이 그 사실을 알린다.

### `core`

가장 자주 쓰이는 안전한 라이브러리. 본 사양이 보증하는 모든 빌드 타깃에서 동일하게 사용
가능해야 한다.

- 숫자, 문자, 문자열 타입과 메서드
- 컬렉션 (리스트, 맵, 셋, 튜플)
- 산술, 비교, 논리, 비트 연산자의 트레잇 정의
- 반복자, 스트림, 미래값
- 동시성 프리미티브 (atomic, mutex, channel)
- 태스크, 병렬 실행의 API 표면
- 형식화, 표시, 디버그
- 리플렉션, 인스펙션

`core/prelude.nok` 의 항목은 모든 nok 소스에서 자동 가시 상태로 시작한다. 사용자가 별도
노출 선언을 쓰지 않아도 이름을 그대로 쓸 수 있다 (예: 가장 흔한 컬렉션 타입과 트레잇).
자동 가시의 정확한 메커니즘은 모듈 시스템 사양에서 정의한다.

### `std`

특정 환경(주로 OS 위)에서만 의미가 있는 영역.

- 파일 시스템
- 네트워크
- 시간, 시계
- 표준 입출력, 환경 변수, 프로세스
- OS 스레드 직접 제어

`std` 의 함수는 타깃에 따라 존재하지 않을 수 있다. 일부 영역이 의미를 가지지 않는 환경
(예: 브라우저 안에서 동작하는 노트북 커널) 에서는 해당 모듈이 빌드되지 않는다.

## 0.5.3. 가시 규약

- `core::prelude` 의 항목은 자동 가시.
- `core` 의 다른 모듈은 명시적으로 끌어와야 사용 가능.
- `unsafe` 는 항상 명시적으로 끌어와야 사용 가능. 위험 시그널을 시각화한다.
- `std` 도 명시적으로 끌어와야 사용 가능. 타깃 의존성을 코드에서 보이게 한다.

"끌어옴" 의 구체 구문(`use`, `import` 등) 은 모듈 시스템 사양에서 정의한다.

## 0.5.4. 제공 형태

세 계층은 사전 빌드된 정적 아카이브로 제공된다.

```
libnok_unsafe.a
libnok_core.a
libnok_std.a
```

이들은 컴파일러 자체와 마찬가지로 의존성 0 원칙을 따른다. 사용자 패키지를 빌드하면 필요한
계층만 링크되고, 결과 산출물은 추가 외부 라이브러리를 요구하지 않는다.

## 0.5.5. 세 계층으로 나눈 이유

- 2 계층(안전, 위험)으로는 "어디서나 쓸 수 있는 안전" 과 "OS 가 있어야만 쓸 수 있는 안전"
  을 구분하지 못한다. OS 의 일부 기능이 없는 환경(브라우저 노트북 등)이 무너진다.
- 4 계층 이상은 사용자가 외워야 할 규칙을 늘리고, 모듈 경계의 가치를 떨어뜨린다.

3 계층은 현장에서 충분히 검증된 구분이며, 가장 단순한 유의미한 분할이다.
