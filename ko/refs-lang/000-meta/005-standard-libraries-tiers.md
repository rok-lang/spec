# 0.5. 표준 라이브러리 계층

표준 라이브러리는 가상 네임스페이스 `rok::*` 아래 세 패키지 계층으로 나뉩니다. 나누는 기준은 쓸 수 있는 환경과 드러내는 동작의 위험도입니다.

## 0.5.1. 세 계층

전체 구조는 다음과 같습니다.

```
  rok::bare   ←   안전 보장 없음. 원시 메모리·FFI·전송 가능 비트 캐스팅·MLIR 직접 접근.
     ↑
  rok::core   ←   모든 타깃에서 사용 가능한 안전 foundation. 내부적으로는 rok::bare 를 쓴다.
     ↑
  rok::std   ←   타깃 종속 계층. 파일 시스템·네트워크·OS 스레드 등.
```

화살표는 의존 방향입니다. `rok::core`는 `rok::bare`를 내부 구현에 쓸 수 있고, `rok::std`는 `rok::core`와 `rok::bare`를 모두 쓸 수 있습니다. 반대 방향의 의존은 금지됩니다.

세 계층 모두 가상 네임스페이스 `rok::` 아래에 있습니다 ([5.7.4 rok::](../005-modules/507-paths.md#574-rok-표준-라이브러리-가상-네임스페이스)). `rok` 자체는 path 루트 컨텍스트 키워드 ([1.5.4](../001-lexical/105-keywords.md))이며, 사용자 식별자와 충돌하지 않습니다.

## 0.5.2. 각 계층의 책임

### `rok::bare`

`rok::bare`는 저수준의 위험한 영역입니다. 컴파일러가 안전성을 보증할 수 없는 동작이 여기에 모입니다. 대표적으로 원시 포인터 형태(raw pointer 추상)와 임의 비트 캐스팅(`transmute` 류)이 있습니다. 핀(pinning), volatile 메모리 접근, C [ABI](007-glossary.md#abi-application-binary-interface) 호환 메모리 할당의 원형도 `rok::bare` 영역입니다. MLIR 다이얼렉트 직접 호출(`rok::bare::mlir`)과 컴파일러의 사용자 정의 다이얼렉트 plugin 로드([stdlib 1.10](../../refs-standard-libraries/100-bare/110-mlir-plugin.md))도 이 계층에 있으며, 외부 텐서 / SIMD / GPU 라이브러리가 가속 영역에 접근하는 통로가 됩니다.

이 계층의 함수를 호출하는 쪽이 안전성을 책임지며, 경로 자체가 이 사실을 분명히 드러냅니다.

### `rok::core` (foundation)

`rok::core`는 가장 자주 쓰는 안전한 라이브러리이며, foundation의 모든 모듈이 여기에 있습니다(예: `rok::core::collections`, `rok::core::iter`, `rok::core::ops`). 본 사양이 보증하는 모든 빌드 타깃에서 똑같이 쓸 수 있어야 합니다. 범위가 넓어서 숫자, 문자, 문자열 타입과 그 메서드, 컬렉션(리스트, 맵, 셋, 튜플)이 들어 있습니다. 산술, 비교, 논리, 비트 연산자의 트레잇 정의와 반복자, 스트림, 미래값도 있습니다. 동시성 프리미티브(atomic, mutex, channel)와 태스크, 병렬 실행의 API 표면도 이 계층에 속합니다. 형식화, 표시, 디버그, 리플렉션, 인스펙션까지 포함합니다.

텐서 / 자동 미분 / SIMD / GPU 같은 가속 영역은 `rok::core`에 들어 있지 않으며, 외부 라이브러리가 `rok::bare::mlir` 위에서 직접 구현합니다. 표준 라이브러리는 일반 코드의 표면 의미만 책임지고, 가속 영역은 라이브러리 layer에서 결정합니다.

컴파일러는 모든 Rok 소스의 시작 지점에 묵시적으로 `use rok::core::**;`를 적용해 `rok::core`의 항목을 보이게 합니다. 그래서 `rok::core::collections::List`를 그냥 `List`로 쓸 수 있습니다. 별도의 prelude 모듈은 두지 않으며, 묵시 recursive glob이 그 역할을 합니다.

`rok::core`의 항목은 기본적으로 `pub`입니다. 외부 패키지에 노출되는 표면이 곧 자동으로 보이는 표면이므로 별도 단계가 필요 없습니다.

### `rok::std`

`rok::std`는 특정 환경(주로 OS 위)에서만 의미가 있는 영역입니다. 파일 시스템, 네트워크, 시간과 시계, 표준 입출력, 환경 변수, 프로세스, OS 스레드 직접 제어 같은 기능이 들어 있습니다.

`rok::std`의 함수는 타깃에 따라 없을 수도 있습니다. 일부 영역이 의미가 없는 환경(예: 브라우저 안에서 동작하는 노트북 커널)에서는 해당 모듈을 빌드하지 않습니다.

## 0.5.3. 가시 규약

가시성 규칙은 다음과 같습니다.

| 영역           | 묵시 import | 명시 import 필요 | 비고                            |
|----------------|-------------|------------------|---------------------------------|
| `rok::core::**` | ✓ 자동      | ✗ 불필요         | `use rok::core::**;` 자동 적용   |
| `rok::bare::**` | ✗           | ✓ 필요           | 위험 시그널을 코드에 보이도록   |
| `rok::std::**` | ✗           | ✓ 필요           | 타깃 의존성이 코드에 드러나도록 |
| 사용자 패키지  | ✗           | ✓ 필요           | 다른 패키지의 항목              |

"끌어옴"의 구체 구문(`use`, `import` 등)은 모듈 시스템 사양에서 정의합니다.

## 0.5.4. 제공 형태와 링크 메커니즘

세 계층은 컴파일러와 함께 배포하는 사전 빌드 정적 아카이브로 제공됩니다.

```
librok_bare.a       (-NL bare)
librok_core.a       (-NL core)
librok_std.a       (-NL std)
```

각 archive는 별도의 패키지 ABI를 가지며, 컴파일러가 빌드할 때 `-NL <name>` 메커니즘으로 자동 링크합니다. 사용자 패키지의 일반 의존성과 분리된 경로이므로, 사용자 패키지가 우연히 같은 이름(예: `mod bare`, `mod std`)을 가져도 충돌하지 않습니다.

세 archive는 컴파일러 자체와 마찬가지로 의존성 0 원칙을 따릅니다. 사용자 패키지를 빌드하면 필요한 계층만 링크되고, 결과 산출물에는 외부 라이브러리가 더 필요하지 않습니다.

## 0.5.5. 세 계층으로 나눈 이유

계층이 둘(안전, 위험)뿐이면 "어디서나 안전"과 "OS가 있을 때만 안전"을 구분할 수 없고, OS 기능 일부가 없는 환경(브라우저 노트북 등)에서 이 구분이 무너집니다. 반대로 계층이 넷 이상이면 사용자가 외울 규칙이 늘고 모듈 경계의 가치가 떨어집니다.

세 계층은 실무에서 충분히 검증된 구분이며, 의미가 있는 분할 중 가장 단순합니다.

모두 가상 네임스페이스 `rok::` 아래에 묶으면 학습 비용이 더 낮아집니다. 사용자는 "표준 라이브러리는 모두 `rok::` 아래"라는 규칙 하나만 기억하면 되고, 그 안의 `bare` / `core` / `std` 책임 구분은 차차 익히면 됩니다.
