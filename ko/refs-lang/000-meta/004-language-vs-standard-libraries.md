# 0.4. 언어와 표준 라이브러리의 경계

이 문서는 언어가 정의하는 것과 표준 라이브러리가 정의하는 것의 경계를 선언합니다. 이 경계는 Rok 사양의 중심 결정이며, 이후의 모든 사양 문서는 이 경계를 전제로 합니다.

## 0.4.1. 언어가 정의하는 것

언어 사양이 직접 다루는 범위는 다음 다섯 가지입니다.

### 1. 로직 흐름

첫째 범주는 값을 흘려보내는 구문과 그 의미입니다. 분기, 반복, 패턴 매칭, 예외 처리, 라벨 점프가 여기에 속하며, 비동기와 생성자(generator)의 구문(선언자와 연산자 키워드)도 이 범주입니다.

### 2. 컨테이너 문법

둘째 범주는 사용자 타입을 정의하는 형태입니다. 곱 타입(레코드형)은 여러 필드를 하나로 묶고, 합 타입(태그형)은 여러 변형 중 하나를 가집니다. 비태그 `union`은 같은 메모리를 여러 형으로 해석하는 장치이고, 트레잇은 동작의 묶음을 선언하며, `impl` 블록은 트레잇과 메서드의 구체 구현을 담습니다. 제네릭은 타입을 파라미터로 받는 형태입니다.

### 3. 메타 시스템

셋째 범주는 앞의 두 범주에 붙어 동작을 바인딩하는 속성(attribute) 체계입니다. 언어가 인식하는 정해진 이름 묶음인 표준 속성과, 사용자 정의 속성과 derive를 위한 템플릿 시스템으로 이루어집니다.

### 4. 변수 / 가시성 / 모듈

넷째 범주는 이름과 노출 규약입니다. 변수 선언 키워드, 참조 수식어, 전역 키워드와 상수 키워드가 여기에 속하며, 가시성 단계와 모듈, 패키지 단위의 이름 노출 규약도 함께 다룹니다.

### 5. 연산자 구문

마지막 범주는 `a + b`, `s[1:3]`, `x.f`, `f(args)` 같은 표기법의 모양입니다.

다만 이 표기법이 어떤 동작을 뜻하는지는 언어가 정의하지 않습니다. 표기법은 표준 라이브러리에 등록된 트레잇 메서드로 desugar되어 의미를 얻습니다.

## 0.4.2. 표준 라이브러리가 정의하는 것

표준 라이브러리는 위 다섯 범주를 뺀 거의 모든 의미를 맡습니다. 숫자와 문자 타입, 그 연산이 여기에 속하고, 산술, 비교, 논리, 비트, 인덱싱, 범위 같은 연산자 의미론도 모두 표준 라이브러리의 트레잇 `impl`로 정의합니다. 형 간 변환 규칙 전체를 담은 변환 매트릭스와 리스트, 맵, 셋, 튜플, 문자열 같은 컬렉션도 라이브러리 영역입니다. 반복자, 스트림, 미래값 같은 추상, atomic·mutex·channel 같은 동시성 프리미티브, 태스크, 스레드, 병렬 실행 API, 입출력·시간·랜덤·네트워크, 그리고 모든 에러 타입도 표준 라이브러리가 정의합니다.

언어는 이 라이브러리 요소들의 이름을 모릅니다. 컴파일러는 메타 시스템의 속성 바인딩으로만 특정 라이브러리 타입을 인식하며, 그 바인딩도 표준 라이브러리 안에 작성합니다.

## 0.4.3. 경계가 만드는 결과

### Syntax 는 언어, 동작은 라이브러리

이 분리의 첫 번째 결과는 표기와 의미를 나누어 맡는다는 점입니다.

> [!IMPORTANT]
> 모든 표기법은 언어가 정의하지만, 값에 가하는 연산의 의미는 표준 라이브러리에 등록된
> 트레잇 메서드가 결정합니다.

| 표기        | 언어가 정하는 것      | 라이브러리가 정하는 것                   |
|-------------|-----------------------|------------------------------------------|
| `a + b`     | 토큰 시퀀스, 우선순위 | `+`가 어떤 트레잇 메서드인지, 결과 타입 |
| `s[1:3]`    | 슬라이스 표기 형태    | 인덱싱, 경계 검사, 결과 타입             |
| `x.f()`     | 메서드 호출 형태      | 메서드 디스패치 규칙                     |
| `let x = 1` | 선언 형태             | 리터럴 `1`의 타입 결정                  |

### 언어 수준 질문의 범위

이 분리의 두 번째 결과는 질문을 나누는 기준입니다. 설계나 구현에서 결정할 일이 생기면, 그것이 언어 수준 질문인지 라이브러리 수준 질문인지부터 구분합니다.

언어 수준에 남는 질문은 다음 영역으로 한정됩니다. 첫째는 컴파일러 의미론(이름 해소, closure capture, 가시성, 에러 진단)입니다. 둘째는 구문 결정(이스케이프, 우선순위, 리터럴 접미사, 슬라이스 표기 모양 등)입니다. 셋째는 런타임 호출 규약과 메모리 모델(객체 레이아웃, calling convention)입니다. 넷째는 리소스 관리(수명, 예외 전파 메커니즘)입니다. 다섯째는 타입 시스템 규칙(트레잇-as-타입 금지, 점진 타이핑, niche 최적화 등)입니다.

### 라이브러리 수준으로 위임되는 것

위 목록 밖의 값 연산은 거의 모두 라이브러리가 결정합니다. 그래서 본 사양은 이런 연산의 의미를 직접 규정하지 않습니다.

대신 사양은 세 가지를 명시합니다. 그 연산이 어떤 트레잇 메서드 호출로 desugar되는지, 그 트레잇을 라이브러리의 어느 계층에서 정의하는지(위치 규약), 정의되지 않았을 때 나는 컴파일 에러의 형태입니다.

이 분리가 Rok의 설계 슬로건 "작은 언어, 풍부한 라이브러리"를 사양 수준에서 구현하는 방식입니다.

## 0.4.4. 구현 한도

언어는 중첩, 사슬 길이, 값 크기, 컴파일 타임 평가에 고정 한도를 두지 않습니다. 구현은 자체 한도를 둘 수 있으며, 그 한도는 언어의 요구가 아니라 구현이 정하는 것입니다. Rok의 한도는 다음과 같습니다.

| 한도 | Rok |
|------|-----|
| parser 중첩 깊이 | 256 |
| 연산자 / 후위 연산 사슬 ([3.2.6a](../003-expressions/302-precedence-and-associativity.md#326a-구현-한도)) | 4096 |
| 값 타입 크기 ([2.6.3](../002-types/206-sum-types.md)) | 펼친 scalar 슬롯 65536 개 또는 4 GiB |
| `const` 평가 ([5.2.4](../005-modules/502-const.md)) | 4,000,000 단계, 호출 깊이 128 |

넘으면 컴파일 에러입니다.
