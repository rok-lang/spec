# 1.8. WASM component model — `ffi.wit`

The WebAssembly Component Model ([bytecodealliance.org](https://component-model.bytecodealliance.org/); Preview 2 stabilized in January 2024) is the foundation for defining typed cross-language interfaces. It replaces the raw pointer + length model that traditional C ABI FFI ([1.7](107-ffi.md)) relies on with rich types: record / variant / resource.

## 1.8.1. WIT — WebAssembly Interface Types

WIT is a language-neutral interface definition language.

```wit
interface fs {
    record stat {
        size: u64,
        mtime: u64,
        is-dir: bool,
    }

    variant error {
        not-found,
        permission-denied,
        io-error(string),
    }

    resource file {
        constructor(path: string);
        read: func(buf-size: u32) -> result<list<u8>, error>;
        close: func();
    }

    open: func(path: string) -> result<file, error>;
}
```

An interface defined this way can be imported or exported from any language: Rust, Go, Python, rok and so on.

## 1.8.2. Binding form on the rok side

First, the import side, which uses an external component:

```rok
// import on the rok side (using an external component)
ffi::wit::import {
    "wasi:filesystem/fs.wit"
}

use wasi::filesystem::fs::*;

let f: file = try file::new("data.txt");
let bytes = try f.read(1024);  // throws (fs::Error) -> List<u8>
f.close();
```

Conversely, the export side, where rok provides a component:

```rok
// export on the rok side (providing a component)
ffi::wit::export {
    "my-pkg/calculator.wit"
}

#[wit::export]
fn add(a: i32, b: i32) -> i32 { a + b }
```

## 1.8.3. Differences between C FFI and WIT

The two approaches differ clearly along several axes.

| Aspect      | C FFI ([1.7](107-ffi.md))    | WIT (this chapter)          |
|-------------|------------------------------|-----------------------------|
| Type system | C primitives + user structs  | record / variant / resource |
| Safety      | **low** (raw ptrs managed by hand) | **high** (typed)      |
| Memory management | malloc/free            | resource (automatic destructor) |
| Error handling | errno / return value convention | first-class result<T, E> |
| String      | null-terminated              | length-prefixed UTF-8       |
| List        | (ptr, len) manual            | list<T> automatic           |
| Call cost   | almost none (direct call)    | trampoline (~ns)            |
| Scope       | every native target          | WASM component runtime      |
| unsafe required | ✓                        | ✗                           |

## 1.8.4. Selection criteria

The criteria are simple: they depend on what is being called and where it is deployed.

| Scenario                    | Recommendation            |
|-----------------------------|---------------------------|
| Calling a traditional C library | C FFI ([1.7](107-ffi.md)) |
| System calls (libc, Win32)  | C FFI                     |
| GPU / SIMD intrinsics       | C FFI                     |
| Safe interface with other languages | WIT               |
| Deployment to WASM environments | WIT                   |
| Plugin / sandbox isolation  | WIT                       |
| Multi-language (Modular / Mojo etc.) | WIT              |

The main significance of this chapter is that rok supports both traditional C FFI and WIT. Users choose either according to their safety, performance and target environment constraints.
